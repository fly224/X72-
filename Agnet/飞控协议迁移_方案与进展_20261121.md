# 放弃 ASCII 单字符命令、改用飞控协议 —— 迁移方案与进展（2026-11-21）

## 一、目标与原则

**目标**：X72 的对外控制接口只保留 MAVLink（飞控协议），删除 55 条单字符 ASCII 命令。

**两条原则**：

1. **不复制逻辑**。ASCII 与 MAVLink 必须共用同一套实现，否则两套会各自演进
   —— 历史上 MIT 切环保护在两条路径上就不一致过（30065 有、ASCII 0x02 帧没有）。
2. **分阶段、可回退**。先让所有功能在飞控协议上可达，再删 ASCII 接收路径。
   任何一步出问题，都能退回上一阶段。

## 二、已完成（阶段 1）

### 2.1 新增统一动作入口

`servo_cmd.h` 定义动作编号，`servo_cmd.c` 实现 `ServoCmd_ExecAction()`：

| 编号 | 动作 | 原 ASCII |
|---|---|---|
| 4 | 电流零点标定 | `C` |
| 5 | 电角度对齐 | `Z` |
| 6 | 磁链 / Kt 辨识 | `+` |
| 7 | R / L 辨识 | `@` |
| 8 | 编码器自校准 | `^` |
| 9 | 摩擦两点标定 | `$` |
| 10 | 机械扫频 | `(` |
| 11 | 摩擦曲线 | `)` |
| 12 | 折算惯量 | `<` |
| 13 | 齿槽转矩 | `}` |
| 14 | 中止辨识 | — |

**实现方式**：`sc_feed_str()` 把动作映射成等价字符，**注入现有 ASCII 队列**。
好处是零逻辑复制、行为逐字节一致、一次覆盖全部 40+ 条命令；
代价是暂时仍会 emit ASCII 回显，且动作是"入队"而非同步完成。

队列的写指针原本只由 USART 接收中断写，这里增加了主循环这一个生产者，
因此用 `__get_PRIMASK` / `__disable_irq` 保护（只有几个字节，关中断 1 µs 量级）。

### 2.2 30069 透传

`app_param.c` 的 `AppParam_ExecSysCmd()` 增加 4..14 的分支，
转发到 `ServoCmd_ExecAction()`。这样 30069 的编号空间与 ASCII 动作一一对应。

### 2.3 上位机动作表

`mavlink_link.py` 的 `FW_SYSTEM_CMDS` 从 4 项扩到 15 项，`action()` 不再拦 4..14。

但 `fric_a` 有 `≥0` 钳位（`:550`）而 `visc` 没有，若有人照报告手填前馈就会写入负阻尼 ——

### 2.7 阶段 2d：30082 扩整数通道（开关/档位），12/12 通过

原来 30082 只有 16 个 float 槽，只能调增益类连续量。`B`（死区补偿）、`%`（5/7 次谐波）、
`{`（起动助推）、`-`（电角补偿）这几个**开关/档位**无路可走，只能继续走 ASCII。

**改动**

| 项 | 内容 |
|---|---|
| 新结构 | `DbgIntParam_t { name, uint8_t(*set)(int32_t), int32_t(*get)(void) }` |
| 新掩码 | `Debug_uint32[15]`（偏移 124），bit i 写 `Debug_int32[i]` |
| float 槽补位 | `[14] eleoff_deg`（原 `-`）、`[15] ff_boost`（原 `{`） |
| 回读扩展 | `Debug_uint32[1]=n_float`、`[2]=n_int`，上位机不用自己维护槽位表 |

**整数槽表（索引即契约，只能追加）**

| 索引 | 名字 | 来源 | 说明 |
|---|---|---|---|
| 0 | `dead_en` | `B` | 死区补偿开关 |
| 1 | `harm_en` | `%` | 5/7 次谐波抑制 |
| 2 | `ff_en` | — | **速度前馈总开关**（此前只能靠 `$` 成功才置 1，状态读不回来） |
| 3 | `cog_en` | — | 齿槽前馈 |
| 4 | `ktc_en` | — | Kt 温度补偿 |
| 5 | `sched_en` | — | 增益调度 |
| 6–15 | `rsv*` | — | 保留，写入被拒 |

**两个设计取舍**

1. **为什么独立掩码**：最常见的操作是"只切换一个开关"。若与 float 掩码共用，
   就必须同时构造 16 个增益值，反而容易把增益写坏。
2. **`G/L/Y` 档位不迁**：它们只是 px 缩放的便捷键，而 30082 已能直接写绝对增益
   （槽 2–5）。UI 上给绝对值比给"第几档"更清楚，也不需要复刻那张缩放表。

### 2.8 阶段 2e：30095 AppTorqueCmd（力矩模式的 id 与斜坡），8/8 通过

**先纠正一个我自己记错的语义**：`"` 的 `tau` 是 **iq 给定的斜坡时间常数（ms）**，
不是力矩。力矩由 iq 经 Kt 换算，给定走 30025。ASCII `"150` 的回显是
`[CMD] cur tau=150ms (0=off, applies to iq_ref only)`，此前文档里一直把它当成力矩给定。

**五条命令的实际归属**

| ASCII | 实际作用 | 迁移去向 |
|---|---|---|
| `>iq` | 使能 + 进力矩模式 + 给 iq（`do_current`） | **30025 已有**（同一条 `do_current` 路径） |
| `/id` | 只改 id，需先在力矩模式 | **30095**（新增） |
| `"ms` | iq 给定的一阶斜坡时间常数 | **30095**（新增） |
| `M` / `N` | ±固定 iq 的快速测试 | 不单独迁：等价于 30025 给那个常值 |

**为什么不为 id 直接启用 30025 的 `idq_tar_A[0]`**：那个位置本来就是 id，但固件一直
只取 `[1]=iq`，等于从未解释过。现在把它打开，所有老脚本发 iq 时那个默认 0 就会顺手把
id 清零 —— 改既有协议语义的风险大于新开一条。所以 iq 留在 30025，id/ramp 走 30095，
不形成两个真值。

**布局** `LEN=12 / crc_extra=95`

| 偏移 | 字段 |
|---|---|
| +0 | u8 mask（bit0 写 id_a、bit1 写 ramp_ms；0 = 只读） |
| +1 | u8 rsv |
| +2 | u16 rsv |
| +4 | f32 id_a |
| +8 | f32 ramp_ms |

应答 10 B：`+0 状态 / +1 写入项数 / +2 f32 id 回读 / +6 f32 ramp 回读`。
回读是**底层钳位后的生效值**，不是本地缓存。

**验证 8/8（`verify_torque_cmd.py`）**

```
基线 id=0.0000 A ramp=20.0 ms
[1] 只写 id=0.5    → 回读 0.5000，ramp 保持 20.0        PASS ×2
[2] 只写 ramp=100  → 回读 100.00，id 保持 0.5000        PASS ×2
[3] 写 id=10 / ramp=5000 → 回读 5.000 A / 2000.0 ms      PASS ×2（钳位生效且回读真值）
[4] 恢复基线                                            PASS
[5] mask=0 纯读不改值                                    PASS
```

**交叉验证（同源）**：30095 写 `id=0.5` → ASCII `>` 空输入查询回显
`cur en=0 iq_tar=0.00 id_tar=0.50 ...` → 再写回 0 → 回显 `id_tar=0.00`。
**同源成立**（两者都调 `Servo_SetCurIdRef`）。

**两个已知语义差异（不是缺陷，是刻意的）**

1. **`/` 有额外前置**：回显 `need >0 first`，必须在力矩模式且有 iq>0 才接受。
   30095 无此约束（与 30082 调参同性质，直调底层）。于是正向验证
   （ASCII `/` 写 → 30095 读）做不成：`>` 之后的 2 s deadman 会在两条命令之间
   把模式退掉，`/` 随即报 `not in torque mode`。已用反向验证替代。
2. **`>` 与 30025 都会自动置 `en=1`**，并带 2 s deadman 自动停机。实测：

   ```
   before      en=0 iq=0
   >0.1 之后   en=1 iq=0.129 A（iqref=0.1）   ← 真的开始输出
   1.4 s 后    en=0 iq=0                      ← deadman 自动停
   ```

   所以力矩给定必须**周期性保活**（与速度模式 `=` 同款），否则 2 s 就掉。
   这一条对写脚本很关键：单次发 30025 只会输出 2 秒。

### 2.11 阶段 3b：30094 AppRecord 录波，9/9 通过（含逐点双通道对账）

替代 ASCII 的 `&`（触发）与 `'`（分频 + 通道编码在百位）。`REC_N=1024`，分频 1..100。

**布局** `LEN=144 / crc_extra=94`，每块 16 点，1024 点共 64 块：

| 偏移 | 字段 |
|---|---|
| +0 | u8 op（0=QUERY 1=START 3=DATA） |
| +1 | u8 arg（START 时=通道 0/1/2；DATA 时=块索引） |
| +2 / +3 | u8 div / u8 ch（当前生效值） |
| +4 | u8 state（0 空闲 / 1 采集中 / 2 有数据） |
| +5 | u8 本帧点数 |
| +6 / +8 | u16 n_pts / u16 n_blk |
| +10 | u16 idx |
| +12 | u8 status（0 成功 / 1 无输出或没数据 / 2 忙 / 3 参数错） |
| +16 | f32 val[16] |
| +80 | f32 th[16]（电角度，仅 ch=1 有意义） |

**单位还原放固件做**：缓冲区是 int16 原始码，三个通道各用各的标度
（ch0 `iq×131`、ch2 `Vq_int×1000`、ch1 `iu×131` + 电角度 `2π→65536`）。
ASCII 时代每个脚本各写一份 `131`，改一处漏一处；现在接口直接给 A / V / rad。

**验证 9/9（`verify_record.py`）**

```
[1] QUERY：div=1 ch=0 n_pts=1024 n_blk=64；ASCII `'` 查询 div=1 一致
[2] X 清故障 → `>` 给 0.3A → `&` 触发 → 36 行 [REC]，解出 871 点
[3] 30094 拉 64 块：1024 点拼齐、无 NaN、max|v|=0.4427 A
[4] **双通道对账（同一份内存）**
    前 6 点 ASCII: 0.2519 0.4122 0.3206 0.2977 0.3359 0.2061
    前 6 点 30094: 0.2519 0.4122 0.3206 0.2977 0.3359 0.2061
    max|差| = 0.000000 @ 24 点
```

第 4 条是这轮最强的证据：ASCII 走 `[REC]` 十六进制、30094 走分块 f32，
**两条完全独立的路径读同一块内存，结果逐点完全相同**。块索引错位、缩放系数错、
符号搞反，这三类错误任何一个都会让它立刻变红。

**过程中撞到一个假象，值得记下来**

`&` 一直报 `REC refused: no output (send W or M first)`，而紧接着的 `>` 回显却是
`CUR on: ... moe=1`，看着自相矛盾。查下去发现 `servo_cmd.c:516` 那行是
**写死的字符串 `"A theta=enc moe=1"`** —— 它永远报 1，哪怕 PWM 根本没开。

真实原因是 `f=0x20`（假超速）让 `>` 被拒，PWM 从未打开，`&` 的拒绝是**正确的**。
已把该处改成读 `BspServo_IsPwmEnabled()`。这是本工程第二次遇到"回显说假话"，
上一次是 `K` 行报调度前 kp。**回显必须读真值，否则排查时间全花在怀疑工具上。**

另外顺带确认一个操作顺序：**力矩给定前若不先 `X` 清故障，`f=0x20` 会让 `>` 直接
被拒**。录波脚本里必须 `X → >iq → &`，三者间隔 < 300 ms（两段式数值命令的超时）
且 `&` 要在 2 s deadman 内发出。

`Code=123788`，0 Error 0 Warning。

### 2.12 阶段 4：删除 ASCII（`X72_ASCII_DEBUG` 默认 0）

**分两步落地，顺序不能反**

**第一步：动作入口改成直调**（`servo_cmd.c` 的 `ServoCmd_ExecAction`）

原来是"把动作映射成等价字符喂进 ASCII 队列"，靠解析器再走一遍。ASCII 一关，
注入的字符就没人解析，动作会静默失效 —— 而且是"帧发出去了、ACK 回 SUCCESS、
电机不动"这种最难查的形态。

改成直接调用 `do_cal()` / `do_align()` / `FluxIdent_Start()` / `RlIdent_Start()` /
`EncCal_Start()` / `FricCal_Start()` / `MechIdent_Start(1..4)`。
联锁（`s_armed != 0` 拒绝）从 9 条 case 里提到入口统一做一次 —— 各写一遍必然漏一条。

**第二步：关 ASCII**

| 位置 | 改法 |
|---|---|
| `servo_cmd.h` | `#define X72_ASCII_DEBUG 0`（默认；改 1 即恢复） |
| `ServoCmd_Poll()` | `handle(c)` 用 `#if X72_ASCII_DEBUG` 包住；**必须在 `MavHost_FeedByte()` 之后** |
| `emit()` | 同样包住，关闭时直接丢弃 |

**为什么关 `handle()` 不会连 MAVLink 一起关**：两者共用一个 USART 队列，
但 `ServoCmd_Poll()` 里 `MavHost_FeedByte(c)` 在 `handle(c)` **之前**执行，
返回 1 就 `continue`。所以 MAVLink 的字节先被取走，剩下的才轮到 ASCII 解析。

**为什么 `emit()` 也要关**：不关的话，`[MI]` 的 30 行、`[REC]` 的 43 行仍会占满
921600 的链路，把遥测和 ACK 挤掉 —— 现象会是"换成飞控协议后反而丢帧变多"。

**效果：Code 从 123244 降到 109332（−13.6 KB）**

不是把代码"屏蔽"了，是 `handle()` 不再被引用，链接器把整条命令实现
（57 个 case、`put_f*` 系列、回显字符串）全部剔除。这反过来证明关断是彻底的。

**验证三项（`verify_ascii_off.py` 语义）**

```
[1] MAVLink 遥测     OK  {en=0 cal=1 z=1 ff=1 cog=1 vbus=30.77 tmot=21.42 fault=0}
[2] ASCII 'S' 回显    (空)  ← 已关闭
[2b] ASCII '>' 回显行数 0    ← 已关闭
[3] 30069 action=12 → 30092 kind=3  J=8.469e-5 acc=1087/2174   PASS
```

第 3 条是关键：ASCII 关掉后动作仍能执行，说明直调路径独立于 ASCII。

**回退方式（不需要 git）**：把 `servo_cmd.h` 的 `X72_ASCII_DEBUG` 改回 `1`，
重新编译烧录即可。代码一行没删，只是被宏包住。

**⚠️ 副作用：34 个 Python 脚本目前全部失效**

它们依赖 `Link.query('S')` 这类 ASCII 调用。状态本身没丢（30090/30091 的字段
在 33/33 对账里已覆盖 `S`/`K` 全部内容），所以 shim 能把这 34 个脚本恢复到
零改动可用 —— 但 shim 本身是独立的一大步，尚未实现。

### 2.13 Python 侧适配：`ident_lib.Link` 改为 MAVLink 后端（已跑通）

**原则**：以后调试通讯一律走 MAVLink。ASCII 只在 `X72_ASCII_DEBUG=1` 用于无上位机时救急。

**`ident_lib.Link` 的改法**：对外签名一个不改（`status/query/run/wait_for/write/s`），
内部全部换 30069/30090/30091/30092，并把结果**合成脚本原本解析的文本行**。
这样用 `Link` 的脚本零改动。

合成文本例（实测输出）：

```

[CMD] spd en=0 wref=0.00rpm wmeas=0.00rpm iqc=0.00 iterm=0.00 ... kp=250.00e-3 ... psi=4.38m kt=92.02m
```

**实测：`ident_elec.py` 跑通**（原样运行，未改一行）

```

交叉验证：R 双口径差 6.8%（判据 ≤10%）、L 差 3.6%（≤25%）、ψ vs 常量 0.9%
综合：WARN（原因是 r² 缺失，见下）
```

**过程中修掉三个真问题**

1. **`30069` 的 ACK 没人读**。ACK 是 `[状态字节, sys_cmd]` 2 B，与请求同 msgid，
   只能靠长度区分。`action()` 原来只返回"帧发出去了"——动作被固件拒绝时帧照样发得出去，
   于是"命令发了、ACK 也有了、电机不动"，只能靠超时猜。已改成等 2 B ACK 并解析 status。
   **没有这一条，下面第 3 条会一直表现成"白等 50 s"。**
2. **辨识之间的最小间隔**。固件执行器仲裁有 `ACT_GRACE_MS=500` 保护窗口，
   上一个辨识跑完也要等 grace 过期才真正 Release。实测 `@` 结束后 0.1 s 发 `+` 会
   Acquire 失败（表现为 OUT_OF_RANGE），0.5 s 后就接受。shim 里补了 0.75 s 间隔。
   另外 `@` 刚停时转子还有 3 rpm 惯性，也是拒绝源之一。
3. **不能拿 0 冒充缺失字段**。30092 的 v[8] 里没有线性度 r²，我最初合成
   `r2=0.0000/0.0000`，脚本就判成"线性度不足（WARN）"——一个看着像测量结果的假 0。
   已改成不输出该字段，让判定看到 None。

**能力边界（写进 docstring，别在这些字段上做判断）**

- 合成 S 行的 `moe` 用 `en` 代替 —— 30090 没有独立的 PWM 位。闭环时两者一致，
  只有 deadman 刚到期那一瞬有差异。
- `bias / ovc / raw / g / clamp` 填 0：这些只服务 ASCII 诊断，需要就直读 30090/30091。
- 逐点行（`[FI]` / `[MI] SW` / `[MI] FR`）不再有：30092 是汇总帧。
  逐点数据要从 30092 的 v[] 或 30093/30094 取。

**⚠️ 覆盖范围：只有 3 个脚本用 `Link`，另有 49 个脚本用 `thermal_soak.Rig`**

`Rig` 是另一套基础设施（自带 rx 线程 + 裸 ASCII 写 + `strip_frames` 解文本），
本次**没有改**。所以这 49 个脚本（`bringup_1000.py`、`thermal_step.py`、
`combo_sweep.py`、`deadband_matrix.py` 以及一批 `diag_*`/`test_*` 诊断脚本）
目前发不出有效命令。

## 五、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 注入方式依赖 ASCII 解析器，删 ASCII 时会一起失效 | 阶段 4 必须重写 ExecAction | 已在文档标注；接口签名不变，只换实现 |
| 动作"入队即返回"，上位机拿不到执行结果 | 现场误判"命令没生效" | 阶段 2 的 30092 事件帧是硬需求，必须配套 |
| 主循环注入与 USART 中断并发写队列 | 队列损坏 | 已用 PRIMASK 临界区保护 |
| 34 个脚本依赖 ASCII 文本格式（正则解析） | 迁移成本大 | 用 Python shim 吸收，不改脚本 |
| 删 ASCII 后失去"telnet 式"现场调试手段 | 现场排障变难 | 保留 `#if` 编译开关，需要时单独编一版 |

## 六、局限

- 阶段 1 只验证了 action=3/4；5~14 走的是同一条注入路径，逻辑上等价但**未逐条实测**
- `+`（action=6）实测后 ψ 仍为 4.38 mWb，无法区分"没执行"与"结果相同"
  —— 后来用同锁内捕获 `[CMD] CAL start` 才确认注入链路本身有效
- 30090/30091/30092 的字段布局是建议稿，未与上位机现有解析对齐
- 未评估删除 ASCII 后的 ROM 收益（预计 3~5 KB，主要在 `put_f*` 与 55 个 case）
