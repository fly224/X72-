## 1. 故障为什么是"过流"

判据（`bsp_servo.c`）：

```c
s_iu = (vu - s_bias_u) * 33.333f;      // 1 mΩ × 30 倍 = 33.3 A/V
if (fabsf(s_iu) > 12.0f || ...) { 8 拍消抖 → FaultSet(OVERCURRENT); }
```

- `s_bias_u` 从参数页恢复 = **1.65 V**（正常中点）
- 当前 `raw_u = 1 cnt` → `vu = 0.0008 V`
- `s_iu = (0.0008 − 1.65) × 33.3 = **−54.97 A**` → 远超 12 A → 持续过流

实测的 `ovc_peak_u = −54.97 A` 与这个计算完全吻合。

**所以"过流"是采样值恒为 0 造成的假象**，不是真实的过流。

## 2. 修复 1：USART ORE 死锁（真缺陷）

### 2.1 原代码

```c
/* stm32g4xx_it.c / USART1_IRQHandler */
if ((USART1->ISR & USART_ISR_RXNE) != 0U) {
    uint8_t b = (uint8_t)(USART1->RDR & 0xFFU);   // 读 RDR 才清 ORE
    ServoCmd_Feed(b);
}
if ((USART1->ISR & (ORE|FE|NE|PE)) != 0U) {
    ServoCmd_NoteUartErr();      // ← 只计数，不清标志
}
```

### 2.2 为什么必死

RM0440 §40.8.6：**ORE 置位后 RXNE 不再更新**。而溢出时 RXNE 本来就是 0，于是：

- 第一段不进（没有 RXNE）
- 第二段只计数，**没有"读 ISR 再读 RDR"**
- ORE 永久保持 → RXNE 永远不置位 → **接收永久停摆**

**现象**：TIM6 中断照跑（遥测 100 Hz 正常、seq 连续），但所有命令无响应、`action()` 收不到 ACK、故障也清不掉。

这与 2026-11-17 那次"主循环钉死"**形态完全相同**，但根因不同（那次是主循环卡，这次是外设标志没清）。

触发条件很宽：主循环忙几毫秒（MavHost 分发、参数页写 Flash）就会积压 → 溢出。

### 2.3 修法

```c
const uint32_t isr = USART1->ISR;
const uint32_t err = isr & (ORE|FE|NE|PE);

if (((isr & USART_ISR_RXNE) != 0U) || (err != 0U)) {
    const uint8_t b = (uint8_t)(USART1->RDR & 0xFFU);   // 一次读，清 RXNE + 所有错误
    if (err) { ServoCmd_NoteUartErr(); }
    if (isr & USART_ISR_RXNE) { ServoCmd_Feed(b); }
}
HAL_UART_IRQHandler(&huart1);
```

**注意**：不要在 `ServoCmd_Task1ms` 里也清 ORE —— 试过，是错的。清 ORE 必须读 RDR，而 RDR 里的字节属于中断；1 ms 任务读一次就会把字节抢走，帧被截断、CRC 全错，表现是"命令时通时不通"，比原问题更难查。

### 2.4 验证

修复后第一次烧录，`action(3)` 返回 **status=0**，`fault` 从 0x0001 清到 **0x0000**，`ovc_peak` 从 −54.97 归零到 0.08 —— **ACK 通道与清故障都恢复了**。

## 3. 修复 2：标定必须检查采样合理性

### 3.1 问题

原 `StartCurrentCal` 采 128 点直接当 bias。采样读到 0 V 时 bias 被写成 0.0016 V，
`iu` 恒为 0，**标定"成功"** —— 真的通电后电流环积分会一路涨到限幅，电机飞车或撞过流，
而现象是"标定通过、使能就炸"，极难反推。

### 3.2 修法

```c
const float bu = s_cal_sum_u / (float)s_cal_n;
const float bw = s_cal_sum_w / (float)s_cal_n;
const float dv = fabsf(bu - bw);

if ((bu < 0.30f) || (bu > 3.00f) || (bw < 0.30f) || (bw > 3.00f) || (dv > 0.20f)) {
    s_cal_state = 0U;                    /* 不写 bias，保持旧值 */
    s_cal_why   = (dv > 0.20f) ? 2U : 1U;
    FaultSet(BSP_FAULT_CUR_SENSE);        /* 新增 bit10 */
} else { s_bias_u = bu; s_bias_w = bw; s_cal_state = 2U; }
```

新增故障位：

```c
#define BSP_FAULT_CUR_SENSE  (1U << 10)   /* 电流采样异常：零点不在中点/两相差过大 */
```

- 窗口 [0.30, 3.00] V 覆盖中点 1.65 V ± 1.35 V
- 两相差 > 0.20 V（≈6.7 A）也判异常

**这一项尚未实机验证**——需要命令通道恢复后才能发 C 触发。

## 4. 修复 3：过流现场接出来

`BspServo_GetOvcInfo()` 原来只在 ASCII 的 `S` 行用，关掉 ASCII 后**过流现场完全不可见**。

现在 30091 的两个槽改报：

| 30091 字段 | 原含义 | 现在 |
|---|---|---|
| `kt@40` | kt (mN·m/A) | **`ovc_peak_u` (A)** 全程最大 \|iu\| |
| `ld@44` | Ld (µH) | **`ovc_raw_u` (cnt)** 对应 ADC 码值 |

代价：30091 不再报 kt/ld，标定值改从 30082 float 13 / 12 读。

**用途**：一眼区分"真过流"（峰值 13~40 A 且码值正常）与"采样链故障"（峰值 −55 A 但码值 0/1）。

## 5. 硬件故障（根因，待查）

### 5.1 数据

| 相 | `ovc_peak` | `raw` | 折算电压 | 正常应为 |
|---|---|---|---|---|
| U | −54.97 A | **1 cnt** | 0.0008 V | 2048 cnt / 1.65 V |
| W | −55.00 A | **0 cnt** | 0.0000 V | 2048 cnt / 1.65 V |
| 母线 | — | 正常 | **30.8 V** | — |
| 温度 | — | 正常 | 21.6 / 25.2 °C | — |

**母线电压和温度都正常**（同一颗 ADC 的其他通道），说明 ADC 本体与基准没问题。
**两路电流同时读到 0 V** → 共因。

### 5.2 可能原因（按概率）

| # | 原因 | 怎么确诊 |
|---|---|---|
| 1 | **运放供电丢失**（V+ 或 V−） | 万用表量运放电源脚，应为 3.3 V（单电源） |
| 2 | **1.65 V 偏置源丢失** | 量偏置节点（分压/REF），应为 1.65 V |
| 3 | 运放芯片损坏（两路在同一片） | 量输入（采样电阻两端应 0 V）、输出（应 1.65 V） |
| 4 | ADC 输入引脚虚焊/短路到 GND | 量 MCU 引脚电压（应 1.65 V） |
| 5 | 采样电阻开路 | 量 1 mΩ 两端通断 |

### 5.3 现场检查顺序

```
1. 断电，量运放供电（V+/V−/GND）
2. 上电但不使能，量偏置节点 = 1.65 V？
3. 量两路运放输出 = 1.65 V？（若不是 → 运放或偏置问题）
4. 量 MCU 侧 ADC 引脚 = 1.65 V？（若运放对而引脚不对 → 串联电阻/焊接）
5. 量采样电阻两端 = 0 V、阻值 = 1 mΩ
```

**判据**：第 3 步若两路输出都是 0 V，问题在运放或偏置（共因）；若只有一路，查该路。

## 6. 未解决的问题：命令通道仍不通

### 6.1 现象

烧录（= 复位）后第一次测试，`action(3)` 成功（status=0，fault 清零）。
但几分钟后再次测试，**所有命令都收不到 ACK，`mode` 也不随 30056 变化**，而遥测始终正常。

### 6.2 已排除

| 假设 | 否定依据 |
|---|---|
| 主循环卡死 | IWDG 250 ms 已启动（`bsp_servo.c:213`），卡死会复位；板子未复位 |
| RXNEIE 被清 | `ServoCmd_Task1ms` 每 1 ms 自愈重开 |
| ack 发送死锁 | `MavHost_Task` 有 30 ms 超时丢弃 + 20 ms gState 自愈 |
| 主循环忙导致溢出 | ORE 已在 ISR 里清 |

### 6.3 矛盾点（诚实记录）

为定位加的寄存器快照显示 `USART1->ISR = 0x0000`、`CR1 = 0x00D0`（UE=0、RE=0），
但**同一时刻遥测在正常发送** —— 这两个事实不可能同时成立，说明**该读数不可信**
（可能读的不是活跃实例，或组帧时机问题）。所以这条线索作废，未能据此定位。

### 6.4 下一步

**断电重启**（不是烧录复位），然后立刻：

```python
lk.action(3)      # 应回 status=0，fault 清零
lk.loop_status()  # 看 30091 的 kt/ld -> ovc_peak / raw
```

若 `raw` 仍是 0/1，说明硬件确定损坏，命令通道的问题被硬件异常掩盖（例如过流每 400 µs 触发一次 `FaultSet`，可能间接影响时序）。**先修硬件，再看命令通道是否自愈**。

# 追加：22:28 编码器异常（0x0002）

**现象** 上位机：`电角度校准（Z）失败` / `故障 0x0002 清不掉（action=3 被拒：确认 MOE 已关）`

## A1. 实测现场

```
fault   = 0x0002  [编码器]
en=0  mode=0  cal=1  z=1  cog=1  vbus=30.8 V
编码器现场: status=0   连续错误=0   连续跳变=3      ← 3 是 2 位字段的饱和值
src=NONE  wmeas=-0.0
pos 10 次采样: 5.982525 ~ 5.982525   抖 0.0 µrad
action(3): status=0（成功） -> fault 仍 0x0002
```

## A2. 判读

| 事实 | 含义 |
|---|---|
| `status = 0` | MT6835 自己报"数据有效"（不是弱磁场/过速） |
| `连续错误 = 0` | 没有"角度越界"帧，`s_enc_err_cnt` 一直是 0 |
| `连续跳变 = 3` | **每帧都在跳变，计数饱和** |
| `pos` 完全不动 | **不是"电机不动"，而是跳变帧被 `return` 丢弃，`s_enc_raw` 冻结在最后一次正常值** |
| `action(3)` 返回 status=0 但 fault 立刻回来 | 清故障本身成功，**下一帧又跳变 → 重新置位** |

判据（`bsp_servo.c:905-915`）：

```c
int32_t d = angle - s_enc_raw;              // 按 2^21 取最短差值
if (d > 65536) {                            // BSP_ENC_JUMP_MAX = 1/32 圈 = 11.25°
    if (++s_enc_jump_cnt >= 3) FaultSet(BSP_FAULT_ENCODER);
    return;                                 // 丢这一帧，角度不更新
}
s_enc_jump_cnt = 0;                         // 只有正常帧才清零
```

**结论：相邻两帧的 21 位角度差持续超过 11.25°。** 电机静止时不可能发生，
所以是**编码器输出或其读取链路异常**，不是控制软件的问题。

## A3. 可能原因（按概率）

| # | 原因 | 依据 |
|---|---|---|
| 1 | **MT6835 EEPROM 校准数据损坏** | 刚做过 `^`（编码器自校准）。若写入中断或校验失败，角度映射会错乱，但 status 仍可能为 0 |
| 2 | 磁铁松动 / 偏心 / 轴向间隙变大 | 最常见，会造成角度在小范围内非单调跳变 |
| 3 | SPI 读取位错位 | `angle` 从 `rx[2..4]` 拼 21 位，若 MISO 上有毛刺或 CS 时序偏移会错位；此时 status 可能恰好是 0 |
| 4 | 编码器供电纹波 | 与前一条电流采样故障可能同源（共用模拟电源） |

**注意**：代码没有校验 `rx[5]` 的 CRC。MT6835 每帧带 CRC，加上校验能直接区分
"帧传输错"与"编码器输出错"——这是下一个该补的诊断（见 A5）。

## A4. 与 0x0001 的关系

两个故障**独立**，但都指向模拟前端：

- 电流采样：U/W 两相输出 0 V（`raw = 1 / 0 cnt`）
- 编码器：角度持续跳变

如果 MT6835 与电流运放共用某路电源/地，一个电源异常可以同时解释两者。
**建议先量电源，再分别查两路信号。**

## A5. 排查与修复顺序

```
① 断电重启，立刻读 fault
     ├─ 仍 0x0002 → 编码器确有问题，继续 ②
     └─ 变 0     → 是运行时跳变，需复现抓幅度
② 断电手动转电机一圈，上电后看 30090.pos 是否跟随
     ├─ 完全不跟随 → 帧全被丢（跳变或 status 错）
     └─ 跳变跟随   → 读数错乱，查 SPI / 磁铁
③ 量编码器供电与磁铁间隙（数据手册要求）
④ 若确认 EEPROM 损坏 → 重做 ^（**前提：电流采样已修好**，否则开环拖动会误判）
⑤ 再重做 Z（电角度），最后重做 }（齿槽表，现在 cog=1 但需确认）
```

**关键顺序**：`^` 和 Z 都依赖电流采样。**电流采样没修好之前不要再跑任何辨识**——
`cal=1` 但采样恒 0，`StartCurrentCal` 的合理性检查会拒绝重标（已加），
而 Z 会按错误的电流值判断丢步/卡死。

## A6. 待补的诊断

| 项 | 价值 |
|---|---|
| **校验 MT6835 帧 CRC**（`rx[5]`） | 一句话区分"SPI 传错"与"编码器输出错"，现在只能猜 |
| 记录跳变幅度（最大 `\|d\|`） | 现在只知道"跳了"，不知道跳多少；11.25° 与 180° 的处理方向完全不同 |
| 把 `enc_jump` 的 2 位字段扩宽 | 现在饱和在 3，看不出"跳了 3 次"还是"跳了 200 次" |

前两项改动都很小，建议下次烧录时一并加上。

# 追加：23:0x 实测 ^（编码器自校准）

## B1. 修了三个问题，才拿到第一个真实结果

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | **`^` 的转速/圈数判据全依赖编码器** | 编码器帧全丢时 `omega=0`、`pos_sum` 不涨 → `EC_ERR_SPEED`。而修编码器又必须先转起来 → **死锁** | 开环拖动时改用**给定电角速度积分**（`s_ol_turns`），不再读编码器 |
| 2 | **`^` 要求 `fault==0` 才能启动** | 编码器持续跳变 → 故障清掉下一帧又置位 → `^` 永远起不来 | 只允许"仅编码器故障"；运行时用 `BspServo_SetEncFaultMask(1)` 暂停该判据（开环拖动本来就不读编码器） |
| 3 | **`^` 的结果从不经 MAVLink 上报** | 只有 ASCII 一行 `[CMD] EC ok`，而 ASCII 默认关闭 → **成功和失败全静默**，上位机只能等超时 | `ec_push_result()`，DONE/FAIL 都推 `30092 kind=7` |

第 3 条是最关键的发现：**以前根本看不到 `^` 为什么失败**。

## B2. 实测结果（Code=118428）

第一轮（2.5 A / 300 rad/s² 斜坡）：

```
ok=0  err=9(TIMEOUT)  turns=—  rpm_avg=600  chip_status=1
elapsed=30001 ms  ol_mode=1（走了开环盲拖）  target=600
```

第二轮（4.0 A / 150 rad/s² / 8 s 斜坡），30 s 内每 300 ms 采样：

| 量 | 实测 | 含义 |
|---|---|---|
| `iq` | **−0.18 ~ +0.36 A** 平稳 | iq 给定是 0，平稳说明电流环在正常工作 |
| `iq_ref` | 0.00 | 同上 |
| `ovc_peak` | **−4.64 A** | 与 id 给定 4.0 A 相符 |
| 电机温度 | 27.5 → 27.7 °C（30 s） | **几乎不升 → 没有堵转** |
| `chip_status` | **1**，30 s 不变 | 芯片报"校准中" |
| `err` | 9（TIMEOUT） | 30 s 超时 |

**结论：电机确实在同步旋转**（电流平稳、无发热），不是拖不动。
600 rpm 下 64 圈只需 6.4 s，30 s 足够 300 圈 —— **但芯片始终不判完成**。

## B3. 卡点转移到芯片侧

代码里 `CAL_EN` 是**纯 GPIO（PB9）**，全项目**没有任何 MT6835 配置寄存器的写入**：

```c
void BspServo_SetEncCalEn(uint8_t en)
{
    HAL_GPIO_WritePin(GPIOB, GPIO_PIN_9, (en != 0U) ? GPIO_PIN_SET : GPIO_PIN_RESET);
}
```

而 `encoder_cal.c` 的注释引用「AUTO_CAL_FREQ = 0x03 的 400~800 rpm 区间」，
**但这个档位从未被写入过** —— 是默认值还是需要在某寄存器里设，代码里没有依据。

1. **`0x113[7:6] = 01` 的准确含义**（是"校准中"还是"已就绪待启动"？）
