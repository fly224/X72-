# 运行时调参接口（30082 AppDebugParam 实现与验证）

> 2026-11-20 23:45 · 起因：Z 对齐时反复改 `CMD_ALIGN_ID` 常量 → 编译 → 烧录，
> 而每次烧录都会擦掉参数页（`cal/z/psi` 全归零），形成"调一个参数、重做一套标定"的死循环。
> 这类"试几个值才知道合不合适"的量必须能在运行时改。

## 一、结论

| 项 | 结果 |
|---|---|
| 协议通道 | MAVLink **30082 AppDebugParam**（192 B = 16×f32 + 16×u32 + 16×i32，双向） |
| 写入语义 | `Debug_uint32[0]` 作掩码，bit i = 1 才写第 i 项；掩码 0 = 纯读 |
| 参数槽位 | 14 个已接通（2 个保留） |
| 越界处理 | 逐项 `set()` 返回 0 → 拒绝并计入 `s_locked`，**不静默截断** |
| 离线验证 | **4/4 通过**（写生效 / 越界拒绝 / 未实现槽位拒绝 / 读回一致） |
| 实机读回 | 16 个槽位全部返回正确值（见下表） |

## 二、为什么必须用掩码

整表写无法区分"写 0"与"不写"。而 0 对多数增益是非法的：`cur_kp` 最小 0.02、
`spd_iqmax` 最小 0.05，直接写 0 会被各自的钳位悄悄改成下限，回读与写入不符，
现场会误判成"写进去了但没生效"。

掩码把"要不要写"和"写成什么"分开，一次可以只改一项。

## 五、踩到的坑（很重要）

**`MavMsg_Find()` 查不到 30082 时，CRC 的 `crc_extra` 取 0（正确值 218）**，导致
192 B 的写帧被判定 CRC 错、静默丢弃。现象极具误导性：**读（4 B 请求帧）正常，写完全不生效**，
而两边的 CRC 算法都没问题——差别只在固件侧的元数据表 `s_meta[]` 里没有登记这条消息。

修法：在 `mavlink_common.c` 的 `s_meta[]` 补一行 `{ MAV_MSG_APP_DEBUG_PARAM, 192u, 218u }`。

同类风险：以后新增任何**接收**方向的 msgid，都必须同时登记 `s_meta[]`，否则会以"CRC 错"的形式失败。
这个约束建议写进协议层文档。

## 六、怎么用

### PC 侧（Python）

```python
import struct, mavlink_proto as MV
p = bytearray(192)
struct.pack_into('<f', p, 4 * 8, 6.1e-4)   # 槽位 8 = ff_acc
struct.pack_into('<I', p, 64, 1 << 8)      # 掩码：只写第 8 项
ser.write(MV.encode(30082, bytes(p), seq=n))
# 回读：发 30000 READ_PARAM(struct_id=30082)，收 30082 的 192 B 应答
```

### 上位机

`POST /api/mavlink/field_send {msgid:30082, values:{...}}` 已可用；
更顺手的是加一个"调参"面板：读一次全表 → 表格编辑 → 带掩码写回。**尚未做**，见待办。

## 七、仍然写死的参数（诚实清单）

| 参数 | 位置 | 为什么还没接 |
|---|---|---|
| `SERVO_KT_ALPHA` | `servo_isr.c:313` | Kt 温漂系数，标定一次就固定，改它会影响已保存的 `Tref` |
| `BSP_CURRENT_TRIP_A` | `bsp_servo.h:44` | 硬件过流阈值 12 A，属安全阈值，不宜给上位机随便改 |
| `BSP_OVC_DEBOUNCE/BLANK` | `bsp_servo.c:163-164` | 抗干扰时间常数，同上 |
| `MI2_*` 机械辨识激励 | `mech_ident.c:60-70` | 幅值/频率扫频表，改动会破坏历史数据可比性 |
| `SERVO_CUR_DEAD_FRAC` | `servo_isr.c:322` | 由 DTG 寄存器算出的物理量，应随硬件走 |

判断标准：**"现场要试几个值才知道合不合适"→ 接运行时；"安全阈值 / 硬件物理量"→ 保持常量**。

## 附：2026-11-21 整数通道扩容（槽 6~15）

float 通道 16 槽已满，而 30082 的载荷是硬布局（16f+16u32+16i32=192 B），
再加 float 槽要动两边协议。后续需求一律走**整数通道的空槽**：

| # | 名称 | 读写 | 含义 |
|---|---|---|---|
| 6 | `comp_mrad` | 读写 | 位置补偿量，mrad（0~100000） |
| 7 | `comp_min_mrad` | 读写 | 补偿行程阈值，mrad |
| 8 | `comp_en` | 读写 | 补偿使能 |
| 9 | `link_diag` | **只读** | 高16=收帧被顶掉次数，低16=长度/CRC 错 |
| 10 | `q_ovf` | **只读** | 命令环形缓冲溢出丢的字节数（正常恒 0） |
| 11 | `uart_err` | **只读** | USART 错误标志累计（ORE/FE/NE/PE） |
| 12 | `rx_ok` | **只读** | 已成功分发的帧数（单调增） |
| 13 | `ps_diag` | **只读** | 低字节=参数加载失败原因(1magic 2version 3crc 4flags)，高字节=Flash 里的 version |
| 14 | `ph_diag` | **只读** | 缺相检测打包，见 `缺相检测_实现与验证_20261121.md` |
| 15 | `ph_trip` | 读写 | 缺相是否升级为故障（默认 0） |

只读槽的 `set = NULL`，写它会拒并计入 `s_locked`；`verify_dbg_int.py` 里
有一条专门验证"写只读槽无效"。上位机名字表 `SerialLink.DBG_INT_NAMES`
必须与固件 `s_dbg_int[]` 逐位对应，`verify_migrated_all.py` 的
"有效槽位数 = 上位机表长"就是在守这条契约。
