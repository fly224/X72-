**固件** `Code=107400` · **日期** 2026-11-22 · **只改固件，未动上位机**

---

## 0. 结论（先看这三行）

1. **固件侧的时间模式是好的**：写入 `t` 立刻生效，实际加速时间与 `t` 严格对应（17/17 项验收通过）。
2. **你截图那一刻，固件里的 `t` 是 60.00 s，不是界面上的 0.40 s** —— `0.40` 从未写进固件。
3. **附带影响**：因为 `t=60` 一直开着，**手调的 a/j 也会被时间模式覆盖**，所以「改 a 也没用」。

## 2. 固件侧实测：t 写入有效、轨迹正确

### 2.1 写入立刻生效

```
设 t=0.40 -> 回读 t=0.400 s   a_eff=7500 rpm/s   j_eff=358099 rpm/s²
设 t=0.80 -> 回读 t=0.800 s   a_eff=3750        j_eff= 89525
设 t=0.20 -> 回读 t=0.200 s   a_eff=15000       j_eff=1432394
```

理论值 `a = 2Δω/t`、`j = 4Δω/t²`（S 曲线，Δω = 1500 rpm = 157.08 rad/s）：
`2×157.08/0.4 = 785.4 rad/s² = 7500 rpm/s` ✓ 三点全部精确吻合。

### 2.2 实际加速时间按 t 走（0 → 1500 rpm）

| 配置 t | 实测 10%→90% | S 曲线理论值 | 偏差 |
|---|---|---|---|
| 0.40 s | 0.230 s | 0.221 s | +4% |
| 0.80 s | 0.434 s | 0.443 s | −2% |
| 1.20 s | 0.654 s | 0.664 s | −2% |

> **注意：10%→90% 不等于 t。** S 曲线（三角形加速度剖面）的整段时间是 `t`，
> 但 10%~90% 只占 `t` 的 **约 0.55**。所以设 t=0.4 s 时看到"0.23 s 就到 90%"，是正常的。
> 判据要看**全程**：0→100% 才是 `t`（实测 0.477 s @ t=0.5 s，见 `verify_speed_traj.py`）。

## 3. 顺手修掉的一个固件缺陷：回读会"说谎"

### 3.1 问题

原来时间模式反算只在「目标变了」时才重算，判据是剩余量 `Δω = |目标 − 斜坡|`。
**电机已经稳在目标转速时 `Δω ≈ 0`，代码回退到配置值**：

```c
if (dw < SERVO_SPD_T_DWMIN) {
    a = s_spd_acc;      /* 回读就变成配置值，与 t 无关 */
    j = s_spd_jmax;
}
```

后果：**改完 `t` 后回读的 `a_eff/j_eff` 永远不动**，任何"到底生效没有"的自查都失效。

实测（修复前，稳态 1500 rpm）：

```
设 t=0.4 -> 回读 a_eff=500 rpm/s（=cfg）  ★ 与 t 无关
设 t=1.0 -> 回读 a_eff=500 rpm/s（=cfg）  ★
设 t=0.2 -> 回读 a_eff=500 rpm/s（=cfg）  ★
```

### 3.2 修法

稳态（`Δω < 0.5 rad/s`）时不再回退配置值，改按「从零到目标」的**名义 Δω = |w_ref|** 反算：

```c
if (dw < SERVO_SPD_T_DWMIN) {
    const float dw_nom = fabsf(w_ref);          /* 名义行程 */
    if (dw_nom < SERVO_SPD_T_DWMIN) {           /* 目标≈0（停机）才回退 */
        a = s_spd_acc;  j = s_spd_jmax;
    } else if (SCURVE) {
        a = 2*dw_nom/t;  j = 4*dw_nom/(t*t);
    } else {
        a = dw_nom/t;    j = s_spd_jmax;
    }
}
```

**不影响实际轨迹**：真正驱动斜坡的是重锁后锁存的 latch，而目标一变
（> `SERVO_SPD_T_RELOCK` = 0.5 rad/s）就会按**真实剩余量**重新反算并覆盖它。

### 3.3 修复后

```
稳态 1500 rpm 下改 t：
  t=0.40 -> a_eff=7500 rpm/s   j_eff=358099   OK
  t=0.80 -> a_eff=3750         j_eff= 89525   OK
  t=0.20 -> a_eff=15000        j_eff=1432394  OK
停机（目标 0）改 t -> 回退 cfg=500 rpm/s     OK（无名义行程，合理）
```

### 还有一个连带问题：`t=60` 会把「手调 a/j」也盖掉

时间模式一旦打开（`t > 0`），就会**覆盖** 30019 / 30089 里手调的 a 和 j。
现在固件里 `t=60`，所以：

- 手调 a=10500 → **不生效**（被 t=60 的反算值覆盖）
- 只有把 `t` 设成 **0** 关闭时间模式，手调的 a/j 才会接管

验证过（`verify_speed_traj.py` 的第 [3] 项）：`t=0` + `acc=400` → `a_eff` 立刻回到 400、
0→200 rpm 只用 0.067 s。

**所以如果你的意图是"用滑条手调 a/j"，必须先把 t 归零**；否则改 a/j 一律无效。

## 5. 如果以后要修上位机（仅供参考，本次未改）

30097 的帧格式（固件侧严格校验长度，长度不符直接当坏帧丢弃）：

| 项 | 值 |
|---|---|
| msgid | **30097**（`MAV_MSG_APP_SPEED_TRAJ`） |
| payload 长度 | **32 B**（必须正好 32，固件按 meta->len 校验） |
| `cmd` | `@off0`，**1 = 写入，0 = 只读回** |
| `t` | `@off4`，float32，秒，0 = 关闭，上限 60 |
| 应答 | 同样 32 B：`status@1`、`t@4`、`a_eff@8`、`j_eff@12`、`t_left@16`、`flags@20`、`acc_cfg@24`、`j_cfg@28` |
| CRC_EXTRA | **97** |
| `flags` | bit0 时间模式开 / bit1 反算被夹 / bit2 S 曲线 / **bit3 时间模式被位置环屏蔽** |

> 上位机能收到 30097 的**查询**应答（截图顶部那行），说明消息号、长度、CRC 都是对的
> —— 那只剩"改 t 时没有真正发出 cmd=1 的写入帧"这一种可能。
