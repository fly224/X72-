显示规则：

- 超过 **1.5 s** 无帧 → 整块显示 `--`（不展示过期值）
- 仿真模式下没有 30025/30027/30040 的量 → 这些行显示 `--`，不伪造 0
- `[DIAG]` 未收到 → 显示「未收到」而不是 `0`；旁注已写明「连上串口后按一次复位键即可刷新」
- 占空比在母线 <5 V 时显示 `--`（反算会放大误差）
- 电角度按 0–360° 归一；原始值为 `14·θm`（范围 ±2520°），归一只为读数直观
- **CRC 校验是软校验**：只统计不丢帧。仿真源不一定遵守 `CRC_EXTRA`，硬校验会把模拟链路全部误杀；真实串口下应为「300 对」且错误数恒 0
- 启动失败现场：`0x00` = 从未失败；`0x1x` = 失败时 `gState` 非 READY，低半字节为 `hdmatx->State`；旧固件没有该字段 → `--`

## 5. 顺带查出的两个隐患（**2026-11-15 11:52 已修复**）

1. **固件 CRC 把 0xFD 魔数算进去了**：原 `telemetry_tx.c:107` 是 `crc_calc(f, 10 + len, extra)`，从帧首 0xFD 开始算；标准 MAVLink v2 从 `len` 字节开始。抓包实证：2134 帧里「含魔数」口径命中 **2134/2134**，「标准口径」命中 **0/2134**。后果：pymavlink / QGC 等标准解析器会把这些帧判为 CRC 错。
   → **已改为标准口径**（`crc_calc(&f[1], 9+len, extra)`），工具链 4 处与页面 `buildFrame` 同步。修复后同一份 300 帧流：标准口径 **300/300**、含魔数 **0/300**。详见 `Agnet/CRC口径与seq修正说明.md`。
2. **单次 seq 跳变 156 帧**（1 次事件，发生在烧录结束瞬间）：`Telemetry_Task1ms` 里先 `s_seq++` 组帧、再 `HAL_UART_Transmit_DMA`，一旦 DMA 启动失败（HAL_BUSY）这 3 个序号就被吞掉——`156 = 52 × 3` 正好对应 52 次失败启动。
   → **已改为发送成功后才推进序号**，并新增 `[DIAG] busy=0xNN` 记录失败现场。修复后 300 帧 seq 断点 **0 处**，本面板「seq 跳变」显示 `0 次 / 缺 0`。

## 5.5 示波器通道（2026-11-15 11:55 接入）

「示波器」页的通道按钮从 7 个扩到 **14 个**，新增的 7 个直接复用面板同一批变量，**不需要新增协议字段**：

| 通道 | 名称 | 单位 | 取值 | 颜色 |
|---|---|---|---|---|
| `iu` / `iv` / `iw` | Iu / Iv / Iw | A | `ax.ia/ib/ic`（30025 +8/+12/+16） | 红 `#ef4444` / 绿 `#22c55e` / 蓝 `#3b82f6` |
| `ua` / `ub` / `uc` | Ua / Ub / Uc | V | `ax.uabcTar[0..2]`（30025 +28/+32/+36） | 浅红 `#fca5a5` / 浅绿 `#86efac` / 浅蓝 `#93c5fd` |
| `cpu` | CPU 占用 | % | `ax.diag.cpuPct`（`[DIAG]` step 行） | 灰 `#94a3b8` |
| `motorTemp` | 电机温度 | °C | `ax.motorTemp`（30025 +53） | 玫红 `#fb7185` |

另外 `temp` 通道已从「温度」改名为「驱动器温度」，明确它指的是板载 NTC_GAN。

设计要点：

- **配色规则**：同一相用同一色相，电流饱和、电压浅一档（U/V/W = 红/绿/蓝）。同时开 `Iu` 与 `Ua` 时，颜色深浅直接告诉你谁是谁的对。
- 实现上是给 `CFG.channelMeta[c]` 增加可选 `get(ax)`；`pushSample()` 优先用它，缺省仍取 `ax[c]`。原有 7 个通道一行未改。
- 默认仍只勾选「转速 + Iq」，其余按下不选，避免一进来就 14 条曲线糊在一起（按钮区 `flex-wrap` 自动折行）。
- `cpu` 通道在没收到 `[DIAG]` 时取 `NaN`，不会被当成 0 画成一条假的零线。
- 「收帧率」在连接后 200 ms 即给出临时值（原来要等满 1 s 窗口，期间显示 `--`）。

验证：用**新固件本体**（`telemetry_tx.c` 编到主机跑）产出的 13300 B 帧流回放，三相电流通道分别落在 +3.000 / −4.000 / +1.000 A（与 harness stub 值一致），量程自动收缩到 −4.54…+3.64；23/23 断言 PASS，其中 `CRC 通过数 == Python std 口径 → 300 vs 300`。

## 7. 局限

- 本轮**未做真实串口联调**：所有验证都是「同一份真实字节」喂给页面解析函数 + 无头浏览器渲染，未在同一时刻让页面与 Python 争用 COM27
- **CRC 修正后仍未抓到实机包**：11:52 已把新固件烧进去，但 COM27 被浏览器 Web Serial 占住（`PermissionError 13`），8 s 抓包没跑成。协议层结论由「固件本体编到主机跑」的字节级回放给出，等价；「实机 DMA 时序下 seq 是否仍连续」待补
- `[DIAG]` 只在开机 3 s 发一次，页面无法主动查询（固件无下行通道）
- 占空比是反算值，不是固件直传；母线低时不可用
- 温度已接入（2026-11-15）：`NTC_GAN`(PA4) / `NTC_MOTOR`(PC4) 双通道，固件按 B 值换算后上送；开路/短路仍送 NaN，面板按 `--` 显示。详见 `Agnet/电机温度接入说明.md`
- 报文无轴号，面板跟随当前选中轴（固件单轴）
- `seq 跳变` 只反映「看到的序号不连续」，不能区分丢帧原因（发送失败 / 线路丢字节 / 主机读慢）
