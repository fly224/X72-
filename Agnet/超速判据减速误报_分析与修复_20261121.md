# 超速故障在减速时误报：分析与修复

**日期** 2026-11-21 · **固件** Code=117924（修复前 117884） · **现象来源** 上位机操作日志
**涉及代码** `servo_isr.c` 的超速判据（`s_spd_wpeak` / `wlim`）

---

## 0. 一句话

不是上位机的问题。**超速门限在减速时会一路衰减，跌破还在正常减速的转速**，于是 0.24 s 就报 `f=0x20`，之后 30019 全部被拒（`status=3`）。

---

## 1. 日志现象

```
18:15:16.605  仅转速  -2100 rpm               成功
18:15:25.646  仅转速  -140 rpm                成功
18:15:25.889  故障出现  无 → 0x0020 超速       故障
18:15:25.923  30019 位置/速度给定 被拒  status=3（状态错误）
```

- `0x0020` = `BSP_FAULT_OVERSPEED`（bit5）
- 从给 -140 到报故障只有 **0.243 s**
- 报故障后 fault≠0，任何 30019 都被前置检查拒绝 → `status=3`（这是**正常的故障保护**，不是第二个 bug）

---

## 2. 复现

用同一序列（1450 → -960 → -2100 → -140，a=580 rpm/s、t=5 s、S 曲线）：

```
-2100 rpm 稳定      wref=-2100.0  wmeas=-2092.7   fault=0x0000
-140 rpm 后 0.24 s  wref=-2091.9  wmeas=-2091.2   fault=0x0020   ← 复现
```

**关键异常：`wref` 还停在 -2091.9 rpm**，说明斜坡才刚起步（走了 0.86 rad/s），根本没到 -140。电机还在正常减速途中被判超速。

---

## 3. 根因

判据（`servo_isr.c`）：

```c
const float aref = fabsf(s_spd_ref_raw);
if (aref > s_spd_wpeak) s_spd_wpeak = aref;   // 升速跟上
else                    s_spd_wpeak *= 0.9999f;  // 降速衰减

const float wlim = 1.5f * base + SERVO_SPD_WMAX_ABS;   // base = peak
if (fabsf(om) > wlim) { 8 拍消抖 → OVERSPEED }
```

`0.9999/拍` → 时间常数 **0.5 s**。给 -140 时给定从 219.9 掉到 14.66，峰值开始衰减：

| t (s) | peak | wlim | 实际 om | 结果 |
|---|---|---|---|---|
| 0 | 219.9 | 340 | 219.9 | 安全 |
| 0.10 | 180 | 280 | 219.9 | 安全 |
| **0.226** | **139** | **218.5** | **219.9** | **超限 → 报故障** |

计算值与实测 0.243 s 吻合到小数点后两位。

### 3.1 为什么"必然"而不是偶发

减速斜率由用户给的 `t` 决定，最小可以到 `SERVO_SPD_ACC_MIN = 5 rad/s²`。要保证减速全程门限不跌破实测，需要

```
τ ≥ V0² / (a · (1.5·V0 + 10))
```

V0=220 rad/s、a=5 时要求 **τ ≥ 28.5 s**，而旧值只有 **0.5 s**，差 57 倍。

### 3.2 第一版修复也是错的（重要）

第一版改成"按给定是否在下降判断"：

```c
if (aref >= s_spd_wpeak)          s_spd_wpeak = aref;
else if (aref >= s_spd_aref_last) s_spd_wpeak *= 0.9999f;   // ← 错
s_spd_aref_last = aref;
```

**实测仍然误报**，加诊断字段看到门限在 192 ms 内从 339.9 掉到 243.5。

原因：`s_spd_ref_raw` 是**阶跃目标**，给 -140 时它一拍就跳到位并保持，所以 `aref < aref_last` **只成立一拍**，第二拍起 `aref == aref_last` 就被当成"减速已结束"，开始衰减。

> 教训：判断"是否在减速"不能用给定（阶跃），必须用**实测速度**或斜坡输出。

---

## 4. 最终修复（Code=117924）

```c
/* 峰值保持：不按时间衰减，按"实测是否已回到给定附近"判断 */
if (aref >= s_spd_wpeak) {
    s_spd_wpeak = aref;                          /* 稳态/升速：跟着给定 */
} else if (fabsf(om) < (1.3f * aref) + 5.0f) {
    s_spd_wpeak *= 0.999f;                       /* 实测已回到给定附近：收回 */
    if (s_spd_wpeak < aref) { s_spd_wpeak = aref; }
}
/* 其余（减速途中 om 远高于给定）：峰值保持不动 */
```

三条行为：

| 状态 | 判据 | 峰值 | 门限 |
|---|---|---|---|
| 稳态 / 升速 | `aref >= peak` | = 给定 | 1.5×给定+10 |
| **减速途中** | `om` 远高于给定 | **保持不动** | 全程不收紧 |
| 减速完成 | `om < 1.3·给定+5` | 0.999/拍收回 | 逐步回到 1.5×给定+10 |

真失控（给定不变而 om 上升）仍会撞线，因为门限始终是 `1.5×给定 + 10`。

## 6. 为什么看起来是"偶发"

旧逻辑下，误报条件是 `1.5×peak·e^(-t/0.5) + 10 < |om|`。它在临界点附近取决于：

- `peak`（历史最高转速）
- 减速斜率 `a = dw / t`（用户给的 t）
- `om` 当时的值

三个量都在变，所以有时躲过、有时撞上。日志里前两次改转速没报、最后一次报了，就是这个原因——不是"某条命令特别危险"。

---

## 7. 顺带确认的两件事

| 项 | 结论 |
|---|---|
| 故障后 30019 被拒 `status=3` | **正常保护**。`do_speed`/`do_pos` 的第一道检查就是 `fault != 0`，清故障（`action=3`）后恢复 |
| 上位机是否有问题 | **没有**。命令序列合法，参数在范围内；是固件判据的缺陷被这个序列暴露 |

## 8. 一个仍然存在的隐患（未改）

超速门限的分支是：

```c
(s_ol_en)                       → 200 rad/s
(s_spd_en || s_pos_en)          → 1.5×base + 10
(s_mit_en)                      → 1.5×|v_des| + 30
else                            → SERVO_CUR_WMAX = 31.4 rad/s
```

最后那个 `else` 覆盖"力矩模式"和"**所有环都不在**"（切模式间隙、刚封锁的几拍）。力矩模式需要 31.4 的固定保护，但切换间隙用同一个门限意味着：

> 在 2100 rpm 运行时切模式，只要中间有几拍 `s_spd_en` 和 `s_pos_en` 同时为 0，`om=219` 就会撞上 `wlim=31.4`，0.4 ms 消抖后报超速。

本次日志没走到这条路径（`do_speed` 在"已在速度模式"时只改给定、不重装），但 `D` 后重新切模式、或速度→位置切换时可能踩到。

**建议**：把 `else` 拆成两支——`s_cur_en` 用 31.4，其余用 `1.5×|om| + 5`（即不判），因为此时通常 MOE 已关、电机自由滑行。待确认实际切换时序后再改。
