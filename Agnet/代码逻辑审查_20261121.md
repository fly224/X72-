## 一、查出并已修的真 bug（2 条，均有实测佐证）

### 1.1 30090 的 controlword 是硬编码的

**位置** `telemetry_tx.c:335`

```c
p_st[0] = (uint8_t)((ServoCmd_IsArmed() != 0U) ? 1u : 0u);   /* 改前 */
p_st[1] = 0u;
```

只填 bit0，其余 15 位恒 0。而上位机是通过 30054 写控制字的（`cw` 是 uint16），
固件也一直保存着真实值（`AppParam_GetControlWord()`）。

**后果**：上位机写 `cw=0x08` 后读回 0，无法区分"没写进去"和"写了被改"。
这属于最典型的"两处不同源"——写进 `s_control_word`，读却从一个布尔推导。

**修复**：改成读 `AppParam_GetControlWord()`（与 30068/30054 的应答同源）。

**实测**

```
30054 写 cw=0x06 → 30090.cw=0x06      （改前恒为 1）
30054 写 cw=0x08 → 30090.cw=0x08      （改前恒为 0）
30054 写 cw=0x06 halt=1 → cw 清 0
```

### 1.2 30093 的块索引在 8 位里溢出回绕

**位置** `mavlink_host.c:659`

```c
got = CogFf_CopyTableMv(mv, (uint8_t)(idx * 8u), 8u);   /* 改前 */
```

`idx` 是 uint8_t：`idx=32` 时 `32*8 = 256` 被截成 **0**，于是**返回第 0 块的数据**。

**后果**：上位机若按错误范围请求（比如把 n_blk 算大了），会拿到重复块，
而且 `status` 仍是成功、`n_bins/valid` 也都正常 —— 没有任何指示。
"静默返回错数据"比崩溃难查一个数量级。

**修复**：先在 16 位里算 `base`，`base < n_bins` 才取；越界时把 `p93[1]` 回填 `idx=0xFF`
作为明确标记（不能只填 0，因为"该块真是全 0"和"越界"无法区分）。

**实测**

```
idx=32 → 回填 idx=255(0xFF)  data 全 0        （改前：返回块 0 的 0.280/-0.317/...）
idx=0  → 回填 idx=0          data 0.280 -0.317 -0.483 0.030
```

## 二、Python 侧 shim 的两个隐患（已修）

### 2.1 会把上一条 30092 当成新结果

30092 是**连发 5 帧**的事件帧。两次同类辨识紧邻时，`last_msg[30092]` 里可能还是上一次的帧，
`_ident_wait` 只按 `ts >= t0-0.6` 判断就会误取旧帧 —— kind 相同，从数值上看不出来。

**修复**：`run()` 发动作前先 `pop(30092)`，只接受本次新帧；时间窗也从 `t0-0.6` 收紧到 `t0`。

### 2.2 脚本给的超时不够（不是 bug，但会误报）

ASCII 时代结束标记是逐行打的，最后一行到得早；现在等的是辨识**完全结束后**才发的一次性
事件帧。实测 `+` 要 15 s，而脚本里写 30 s，在 `@` 刚跑完接着跑 `+` 的工况下不够，
脚本会误报"未给出完整结果"。

**修复**：`run()` 取"脚本值"与"内置下限"中较大者。

## 三、测试自身的漏洞（比代码 bug 更值得记）

**回归脚本的对账基准已经消失。** `verify_migrated_all.py` 原来拿 30090/30091 去对
ASCII 的 `S`/`K` 行；ASCII 关闭后这两行恒为空，于是 **21 项全部 FAIL**——
看起来像固件崩了，实际是基准没了。

**已改成"自洽 + 跨消息交叉"**，这比文本对账更强：文本是同一份数据的另一种呈现（同一路径），
而 30090/30091/30082 是三条独立路径。

另外那条 `cw & 1 == en` 判据本身就是坏的：`en=0` 时 `cw` 也是 0，**恒成立**，
所以 1.1 那个 bug 藏了两天没被发现。已换成"写 cw 再读回"的往返测试。

改完 **26/26 通过**。

## 四、我自己的一次操作错误（教训比 bug 大）

**把 30068 当成控制字发了。**

- `30068` = **AppPermissionConfig**（权限配置，2 字节）
- `30054` = **AppControlWord**（控制字，3 字节）

两个名字都像"控制"，我发了一帧 3 字节的 `cw=6` 到 30068，固件按权限帧解析：
`comm_auth=6` → `has_host_auth()` 从此返回 0 → **上位机把自己所有写操作权限关掉了**，
后续 30054/30069 全部静默失效。

**恢复方法**：发 30068，载荷 `[0, 0]`（comm=0 表示上位机接管）。

**为什么会踩**：这两个消息号在文档里并排，而 `mavlink_link.set_controlword()` 的实现是
正确的（发 30054），我手搓帧时凭印象挑了 30068。**以后手搓帧一律先查 `s_meta`/CSV 的长度字段**
（2 B vs 3 B 是硬区分），不靠记忆。

## 六、明确排除的（查过、确认没问题）

- **`s_id_pay` 无竞态**：`Telemetry_PushIdentResult()` 与 `Telemetry_Task1ms()` 都在
  `Servo_SlowTask1ms()` 里串行执行（`servo_isr.c:2704/2730`），不存在中断打断。
  临界区里的 PRIMASK 属多余但无害。
- **30082 的两个掩码不冲突**：float 掩码在 `uint32[0]`（偏移 64），int 掩码在
  `uint32[15]`（偏移 124），有效槽位数在 `uint32[1]/[2]`（72/76）。
- **30095 应答长度**：`resp_len=10`，局部 `resp[16]` 够；30093/30094 走 `ack_prepare`
  的 `s_ack[204]`，144 B 载荷也够。
- **ASCII 关闭不会连 MAVLink 一起关**：`MavHost_FeedByte(c)` 在 `ServoCmd_Poll()` 里
  先于 `handle(c)` 执行且 `continue`。
- **`AppParam_Init()` 清 `s_control_word` 只在启动**：运行时只有 halt 与正常写入两处赋值，
  不存在每拍清零。
