## 0. 结论先行

**固件协议层 = 翻译层 + 门卫，不是控制逻辑。** 它只做两件事：把总线上的字节流翻译成「对 database 的一次读/写请求」，再把内部状态翻译回总线帧。它**不允许**直接读写应用变量、不允许做控制运算、不允许决定电机怎么动。

当前工程 `communication/`、`database/` **均为 0 文件**（上一轮 NO-GO 判定的第 8 项）。所以上位机现在即使把 91 条消息的帧发到串口/CAN，固件里也没有接收端，帧会被丢弃。

一个关键约束：**不能直接照搬参考工程的协议层**。参考工程围绕 `kAxis` 结构体 + CanFestival + FlashDB 构建，而本工程的控制律是新的 ERT 单模型 `three_loop_deploy`（`ExtU/ExtY/step()`），底层只有 CubeMX 配好的裸 FDCAN1 与 USART1。协议层要写成「同一套 database 接口 + 新的控制律桥接」。

## 1. 职责边界（四层 + 数据库）

| 层 | 负责 | 明确不许做 |
|---|---|---|
| `app/` 应用层 | 规划：CiA402 运行模式、辨识流程、保护扫描、参数存储 | 不做控制运算 |
| `motor_control/` 控制层 | 控制状态机与 API，调用算法库 | 不做规划、不解析协议 |
| `communication/` 通讯层 | 帧编解码、msgid 分发、协议状态机、错误重同步 | **不直改应用变量**、不做单位换算以外的业务 |
| `board_public/` 驱动层 | `bsp_api.h` 抽象：USART1/FDCAN1/SPI/TIM/ADC 的收发与中断 | 不认识协议语义 |
| `database/` 数据库 | `set_app_*` / `get_app_*` —— 上位机与总线访问内部参数的**唯一通道**；状态检查、范围检查、单位换算、持久化 | 不解析帧、不做控制 |
| `simulink_code_gen/` | 生成的算法库 | 禁手改，重生成即覆盖 |

`AGENTS.md` 核心原则第 2 条：「所有参数读写必须走 database 的 get/set 回调，不允许协议层直接改应用变量」；禁止事项第 2 条：「禁止绕过 database 回调直接改应用参数（协议层/上位机路径全部失效）」。

**物理类比**：database 是配电柜里唯一的接线端子排，协议层是外面的插头转换器。插头可以换（MAVLink / CANopen / EtherCAT），但所有线必须接到同一排端子上；谁要是把线直接焊到电机绕组上（协议层直改变量），上位机读数、参数保存、保护逻辑就全部旁路失效。

## 2. 三条通道与硬件映射

| 通道 | 物理接口 | 本板 CubeMX 配置 | 开关 | 参考实现 |
|---|---|---|---|---|
| MAVLink v2 上位机调试 | FDCAN1 FIFO1 透传（MAVCAN）**或** RS485 `USART1` PB6/PB7 @921600 | FDCAN1 PA11/PA12，1 Mbps，`FD_NO_BRS`；USART1 921600 + DMA1_Ch5/6 | `version.h` 中 `IS_USE_CAN_PASSTHROUGH`；开启 = CANFD 透传，关闭 = UART1 | `communication/callback/mavlink/mavlink_callback.c`（1627 行） |
| CANopen CiA402 从站 | FDCAN1 FIFO0 | 同上 | `MINOR_VERSION = V_CANOPEN_CIA402` | `communication/protocol/CANopen/`（CanFestival）+ `callback/canopen/canopen_callback.c` |
| EtherCAT | 占位 | — | `V_ECAT_CIA402` | `protocol/EtherCAT_LAN925x/` |

`version.h` 还定义 `IS_USE_MAVCAN_CLASSIC_FRAME`：与经典 CAN 节点共总线时用 8 字节分包，避免 FD 帧让经典节点报错帧。

**本工程现状**：`.ioc` 只配了 FDCAN1 与 USART1 两个物理外设，**没有** CanFestival、没有对象字典、没有 MAVLink C 库。第一阶段建议只做 MAVLink 通道（与已完成的 91 条上位机字段层直接对接）。

## 3. 参考工程里的真实代码形态（已核验）

### 3.1 收包入口（`mavlink_callback.c:119`）

```c
void MavlinkRecvCallback(Axis *axis, AxisDw *axis_dw, uint8_t rx_data[], uint32_t len)
{
    for (uint32_t i = 0; i < len; i++) {
        if (mavlink_parse_char(MAVLINK_COMM_0, rx_data[i], &msg, &status)) {
            is_mavlink_parse_success = true; break;
        }
        else if (++mavlink_parse_fail_cnt >= MAVLINK_PARSE_ERROR_THRESHOLD) {
            mavlink_reset_channel_status(...);   /* 噪声后重同步 */
        }
    }
    ...
}
```

要点：**逐字节流式解析**、失败计数超阈值重置通道状态（噪声/断帧后能自恢复）。这条逻辑应原样保留。

### 3.2 两条分发路径

- **读**：`msg.msgid == 30000 READ_PARAM` → `mavlink_msg_read_param_decode()` 取 `struct_id` → `switch(struct_id)` → `get_app_*()` 填结构体 → `mavlink_msg_<name>_encode()` 回发。
- **写**：`switch(msg.msgid)` → `mavlink_msg_<name>_decode()` → **权限检查** → `set_app_*()` → **回读 `get_app_*()`** → encode 回发。

回读这一步很重要：写入被拒（只读/超范围/使能态）时，上位机收到的是固件里的**真实值**，不会误以为写成功了。

### 3.3 权限与状态门卫

```c
if (get_app_Comm_control_authority() == COMM_CONTROL_HOST)
    set_app_MIT_kd(app_motion_param_t.MIT_kd);
```

`30068 AppPermissionConfig` 是写权限总闸（0=上位机接管）。`data_param.c` 的 `set_app_*` 内部再做第二道检查：

```c
if (axis->motor_ctl_sm_output.state == MOTOR_CTL_SM_MOTOR_ENABLE)
    return APP_PARAM_WRITE_STATE_ERROR;      /* 使能态禁止改额定参数 */
if (val > load_encoder_resolution || (val != 0 && load_encoder_resolution % val != 0))
    return APP_PARAM_OUT_OF_RANGE;
```

`APP_PARAM_STATUS` = 成功 / 只读 / 超范围 / 状态错误，四种结果都要能回给上位机。

### 3.4 与驱动层解耦

`RegisterSendCallback()` / `CallSendCallback()` 把「组好的帧」交给底层发送函数，协议层不需要知道是 CANFD 还是 RS485。CANopen 侧同理，`canopen_callback.c` 只有 14 行：

```c
UNS32 SlaveOD_Read_Callback(uint16_t index, uint8_t subindex, void *data)
{ return master_cia402_read_callback(index, subindex, data); }
```

字典回调统一转发到 `master_cia402_*`，最终仍落到 `set/get_app_*`。

### 3.5 生成文件纪律的实物差异（需注意）

`AGENTS.md` 说生成文件「只能改 `USER CODE BEGIN/END` 区」，实测：
- `data_param.c` 确实有 `/* USER CODE BEGIN set_app_xxx */` 区 ✅
- `mavlink_callback.c` **0 个 USER CODE 区**，用的是 `//DATABASE_CODE_START_1` 分段标记

所以本工程若复用 `mavlink_callback.c`，不能按文档想当然地找 USER CODE 区；要么整体由生成工具重新生成，要么自己写一层薄回调包住它。

## 5. 编写顺序

`AGENTS.md` 第 151 行给出的移植顺序是 `common → communication → database → motor_control → BSP → app`。结合本工程实际：

1. **common**：定长环形缓冲、CRC/X25、字节序工具。全部静态分配，不用 `malloc`。
2. **communication/protocol/MAVLink**：复用参考工程 `servo_hub_database/` 的 91 个 `mavlink_msg_*.h` + `protocol.h` / `checksum.h` / `mavlink_helpers.h`，实现 `mavlink_parse_char` 流式解析与 `mavlink_msg_*_encode` 组帧。
3. **database**：写 `app_param.h/.c`，定义 `APP_PARAM_STATUS`、`set_app_*` / `get_app_*` 原型与参数存储（FlashDB，片内 Bank2 末 64 KB）。状态检查、范围检查、单位换算全部收敛在这里。
4. **communication/callback/mavlink**：写 `MavlinkRecvCallback` 分发；每个 case 走「decode → 权限 → set → 回读 → encode 回发」。
5. **board_public 绑定**：`RegisterSendCallback()` 指向 FDCAN1 或 USART1 的发送；接收侧 DMA/中断只把字节压入环形缓冲，**解析放在 1 ms 非实时任务**（TIM6/TIM16），不在 ISR 里解析协议、不 `printf`、不阻塞 SPI。
6. **app 接入**：运行模式、保护扫描、参数存储；`CheckTable[]` 错误位序与上位机错误码表同步。
7. **控制律桥接**：`pos_ref` / `en` / 增益 → `three_loop_deploy_U`；`Y.iq_ref` / `Y.ticks` → `AppStatusInfo` / `AppMotionInfo` 遥测。写参数后若涉及额定值，调 `MotorCtlParamSetUpdata(&kAxis)` 等价的更新钩子。

/* communication/callback/mavlink/mavlink_host.c —— 分发骨架 */
void MavlinkHost_Task1ms(void)               /* 由 TIM6 1ms 任务调用，非 ISR */
{
    uint8_t byte;
    while (RingBuf_Pop(&g_rx_ring, &byte)) {
        if (!mavlink_parse_char(MAVLINK_COMM_0, byte, &g_msg, &g_status))
            continue;                        /* 带失败计数与通道重同步 */

        switch (g_msg.msgid) {
        case 30000: MavlinkHost_OnReadParam(&g_msg); break;   /* 回发结构体 */

        case 30069: MavlinkHost_OnSystemCmd(&g_msg);   break;
        default:    break;                              /* 未实现消息静默丢弃 */
        }
    }
}

## 7. 硬实时与工程纪律

| 约束 | 要求 |
|---|---|
| ISR 最小化 | 收中断只入队；解析、database、回发全在 1 ms 任务；禁止在 ISR 内 `printf` / 阻塞 SPI / 等待信号量 |
| 静态内存 | 定长环形缓冲 + 静态消息对象；`mavlink_tx_buff` / `rx_buff` 固定大小（参考工程用 `.RAM_D1` 段） |
| 错误恢复 | 解析失败计数超阈值重置通道状态，噪声后能重新同步 |
| 回发节拍 | 心跳 1 Hz、状态/运动反馈 10~100 Hz；**绝不在 20 kHz 电流环 ISR 里发帧** |
| 参数纪律 | 权限总闸 30068 + 使能态拒写 + 范围检查；额定参数变更后调更新钩子 |
| 单位换算 | 内部浮点 + 电机端单位；CiA402 字典 ×1000 定点，换算收敛在 database / `unit_conversion` 边界，防除零 |
| 错误位序 | `CheckTable[]` 顺序 = 上位机错误码表顺序，增删须同步 |
| 编码风格 | 注释中文、标识符英文；函数前缀 `app_/bsp_/set_app_/get_app_/MotorCtl*`；最小改动 |

## 8. 验证清单（可量化）

1. 帧层环回：用已完成的 `host/mavlink_proto.py` 作对端，固件回发帧应能被 `FrameParser` 解析且 CRC 通过。
2. 消息表一致性：固件 91 个 `mavlink_msg_*.h` 的 LEN / crc_extra 与 `mavlink_layouts.json` 逐条比对（应 91/91）。
3. 门卫用例：未开权限写参数应被拒并回读原值；使能态写额定参数应返回 `APP_PARAM_WRITE_STATE_ERROR`；保存后掉电重启参数保持。
4. 上位机联动：用 `field_console.html` 逐条读 9 条首期消息，字段值与固件一致。
5. 实时性：`DWT->CYCCNT` 测 1 ms 任务里协议处理最坏耗时，确认不影响 20 kHz 电流环。
