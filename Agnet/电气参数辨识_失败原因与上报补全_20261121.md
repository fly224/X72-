# 电气参数辨识（`@` R/L）失败：原因分类与上报补全

**日期** 2026-11-21 23:2x · **固件** Code=119204 · **串口** COM27 @921600
**范围** `@`（action 7，R/L）为主，兼及 `+`（6）、`^`（8）、`<` `)` `(` `}`（10~13）

---

## 0. 结论先行

**当前这台机器上，`@` 是成功的**：R=290.5 mΩ、L=91.9 µH、Z=0.646 Ω、60/60 有效点、0.38 s。

之前所谓的"失败"，**最可能是前置检查被拒**（`fault != 0`），而不是算法跑错。而它**查不出来的原因不在算法，在上报**：

> 9 个辨识 kind 里，有 **6 个在失败时一条 MAVLink 消息都不发**；启动被拒时，子模块的 7 种错误码又被压成同一个 `status=2`。
> 两件事叠加的结果是：**失败 = 静默**，上位机只能显示"失败"或"超时"。

本轮把两条路径都补齐了。

---

## 1. 现场实测（Code=119204）

### 1.1 正常路径

```
action(7) -> status=0
30092 kind=2 ok=1 n=60
  R_mOhm  = 290.5      L_uH   = 91.9
  Z_ohm   = 0.646      iamp_A = 1.54
  Vavg_V  = 0.578      Iavg_A = 1.99
  inj_amp = 1.000
```

多次重复：**280.2 / 283.2 / 290.5 mΩ，91.9 / 92.8 / 93.5 µH**（分散约 ±2%，主要是绕组温度）。

### 1.2 启动被拒路径

连续两次发 `@`（间隔 20 ms），第二次 `RlIdent_Start` 返回 `BUSY`：

```
30092 kind=2 ok=0 n=0
  v[0] = 1        <- RL_IDENT_ERR_BUSY，错误码已带上
```

**修改前**：这条信息完全没有出口。

### 1.3 运行期失败路径

启动后 60 ms 发 `halt=1` → `do_disable` → `RlIdent_Abort()` → `rl_fail(TIMEOUT)`：

```
30092 kind=2 ok=0 n=0
  v[0] = 8        <- RL_IDENT_ERR_TIMEOUT（Abort 的既定码）
  v[1..7] = 0     <- 中止发生在 R 段未跑完时，现场量尚未填
```

## 2. 失败原因分类（`@`，7 种启动码 + 1 种运行码）

| err | 名称 | 触发条件（代码位置） | 现场表现 | 处理 |
|---|---|---|---|---|
| **1** | BUSY | `RlIdent_IsBusy` 或 `IsPwmEnabled` | 另一个辨识在跑，或 MOE 还开着 | 等前一个结束 / 先 `halt` |
| **2** | CAL | `IsCurrentCalibrated()==0` | 没做 `C` | 发 `C`（action 4） |
| **3** | ZERO | `IsEncoderZeroed()==0` | 没做 `Z` | 发 `Z`（action 5） |
| **4** | FAULT | `GetFault()!=0` | **任何故障位非 0** | 先清故障（action 3），再查为什么会有故障 |
| **5** | PWM | `PwmEnable(1)` 后 `IsPwmEnabled()==0` | MOE 打不开 | 多半是 `s_fault` 残留，回到 err=4 处理 |
| **6** | CURRENT | R 段电流没建立 | `i_avg` 远小于 `CMD_RL_TEST_A` | 功率级 / 接线 / 采样链 |
| **7** | FIT | L 有效点太少或离散过大 | `l_points` 很小 | 注入幅度不足或电流噪声大 |
| **8** | TIMEOUT | 阶段超时 / 被 Abort | — | 查是否被 `halt` 打断 |

`CMD_RL_TEST_A` 是本次测试电流（`RL_ID_MIN_A ~ RL_ID_MAX_A` 之间夹取）。

### 2.1 结合这块板的历史，最可能是哪一条

| 时间点 | 板子状态 | `@` 会报 | 依据 |
|---|---|---|---|
| 编码器故障期 | `fault = 0x0002`（一直清不掉） | **err=4 FAULT** | `RlIdent_Start` 第 5 条检查就是 `GetFault()!=0` |
| 电流采样故障期 | U/W 两相 0 V，`iu = −55 A` | **err=4 或 6** | 采样坏 → 过流故障（4）；或开环 id 拉不起来（6） |
| **现在（两者都恢复）** | `fault=0`、`raw_u=2031 cnt`、`enc_jump=0` | **成功** | 本节 1.1 |

所以"电气参数辨识失败"**不是辨识算法本身的问题**，是被上游故障挡住了。这也解释了为什么它时好时坏。

## 3. 本轮修的三个上报缺口

### 3.1 运行期失败：6 个 kind 全部静默

| kind | 入口 | 修改前 | 修改后 |
|---|---|---|---|
| 1 FLUX | `+` | 只 emit ASCII | 推 30092 ok=0 |
| **2 RL** | **`@`** | **只 emit ASCII** | **推 30092 ok=0** |
| 3 惯量 | `<` | 只 emit ASCII | 推 30092 ok=0 |
| 4 摩擦曲线 | `)` | 只 emit ASCII | 推 30092 ok=0 |
| 5 齿槽 | `}` | 只 emit ASCII | 推 30092 ok=0 |
| 6 扫频 | `(` | 只 emit ASCII | 推 30092 ok=0 |
| 7 编码器 | `^` | 只 emit ASCII | 本轮前一节已补 |
| 8 电角度 | `Z` | 已推 | — |
| 9 摩擦标定 | `$` | 已推 | — |

为什么必须修：`X72_ASCII_DEBUG = 0`（2026-11-21 起默认关闭），**ASCII 通道整体不存在**。所有"只 emit"的失败信息等于扔进黑洞。

### 3.2 启动被拒：错误码被压成一个 `status=2`

`AppParam_ExecSysCmd` 的映射：

```c
if (r == SC_EXEC_ACCEPT)      { return APP_PARAM_SUCCESS; }        /* 0 */
if (r == SC_EXEC_NEED_DISARM) { return APP_PARAM_WRITE_STATE_ERROR; } /* 3 */
return APP_PARAM_OUT_OF_RANGE;                                     /* 2 */
```

`SC_EXEC_REJECT` 把 8 种错误码压成 `2`。现在改为：**先推一帧 `ok=0, v[0]=err`，再返回 REJECT**。

覆盖 `FLUX / RL / ENC_CAL / FRIC_2PT / MECH×4`，以及 `do_align()`（`Z` 的两条拒绝路径原来也只 emit，见《电角度校准_上位机指令集》§1.1 记录的坑）。

### 3.3 失败帧的字段约定

统一为：**`v[0] = 错误码`，其余槽位放"已经测到的现场量"**，未定义的填 0。

| kind | 失败时 v[] |
|---|---|
| 1 FLUX | err, n_done, psi_mWb, R_mOhm, L_uH, dev_pct, dbg_om, dbg_wref |
| 2 RL | err, R_mOhm, L_uH, Z_ohm, iamp_A, Vavg_V, Iavg_A, inj_amp |
| 3/4/5/6 机械 | err, mode, cog_n, fric_n, sweep_n, J_e4, visc, 0 |
| 7 ENC_CAL | err, rpm_avg, rpm_min, rpm_max, chip_status, elapsed_ms, ol_mode, target_rpm |

**接收侧必须先看 `ok` 再解释 `v[0]`** —— 同一个 kind，`ok=1` 时 `v[0]` 是结果量，`ok=0` 时是错误码。

### 3.4 `@` 失败帧怎么读（这是本轮最实用的一条）

`rl_fail()` **不清 `s_res` 的测量字段**，所以失败帧里的 `v[1..7]` 是真实现场：

| 现象 | 含义 |
|---|---|
| `v[1] = 0`（R 还是 0） | 连 R 段都没跑完 → 看 err，多半 4/5/6 |
| `v[1]` 有值、`v[2] = 0` | R 段过了，注入段失败 → 看 `v[4]`（注入电流幅值） |
| `v[4] ≈ 0` | 电压注了但没有电流 → 功率级未接通 / 采样链坏 |
| `v[7]`（inj_amp）≠ 预期 | 注入幅度被改过（`#` 键或 `RlIdent_SetInjAmp`） |

## 4. 上位机侧的一个坑（不是固件问题）

`mavlink_link.py` 的 `action()` 用 `last_ack` 判 status，条件是：

```python
if a and a.get("ts", 0) >= t0 - 0.05:      # 容忍 50 ms 的旧 ACK
```

**后果**：20 ms 内连发两次同一动作，第二次会读到**第一次的 ACK**，`status` 显示 0（成功）而实际被拒。

本轮实测就撞到了：第二次 `@` 实际返回 `BUSY`（30092 里有 `ok=0 err=1`），但 `action()` 报 `status=0`。

> **所以判断"动作是否被接受"不能只信 `action()` 的 status**：
> `status=0` + 没有 `ok=1` 结果帧 + 有 `ok=0` 帧 ⇒ 实际被拒。
> 想彻底修，把容差从 `0.05` 改成 `0`，或按请求 seq 匹配应答。

## 5. 复现与验收脚本

```python
import time, struct
from mavlink_link import SerialLink

lk = SerialLink(); lk.connect("COM27", 921600); time.sleep(3.0)
lk.set_permission(0, 0)
lk.action(3); time.sleep(0.4)          # 清故障（err=4 的对策）

t0 = time.time()
r  = lk.action(7, timeout=3.0)         # @
print("status =", r.get("status"))     # 0 = 已入队（注意 §4 的坑）

seen = {}
while time.time() - t0 < 2.0:
    m = lk.last_msg.get(30092)
    if m and m["ts"] >= t0 and m["ts"] not in seen:
        seen[m["ts"]] = 1
        raw = lk._payload_of(m)
        if raw and len(raw) >= 40:
            v = struct.unpack_from("<8f", raw, 4)
            print("ok=%d err/v0=%.0f R=%.1f L=%.1f" % (raw[1], v[0], v[1], v[2]))
            break
    time.sleep(0.01)
```

**每次结果会连发 5 帧相同内容**（抗丢帧），接收侧按内容去重即可。
