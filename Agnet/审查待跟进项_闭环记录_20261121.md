## 一、新查出的三个真 bug

### 1.1 命令环形缓冲只有 32 B，而一条 30094 请求是 156 B ★根因

**位置** `servo_cmd.c:64` `#define CMD_Q_LEN 32U`

ASCII 时代单字符命令最长 8 B，32 B 缓冲绰绰有余。迁到飞控协议后最长的请求是
30094 AppRecord：`12 + 144 = 156 B`。环形缓冲满了的处置是"丢新字节、不覆盖未处理的"，
而这条路径**没有任何计数**。

于是只要接收期间主循环有 >350 µs 的阻塞（发送一条 156 B 应答本身就是逐字节轮询
TDR 约 1.7 ms），一帧请求就会被吃掉中间几十个字节。四个计数里只有一个是稳定的：

| 计数 | 现象 |
|---|---|
| 固件 CRC 错 | **时有时无**（同一 bug 下先测到 0、A/B 时测到 3）—— 不能作为判据：截断后能不能凑出一帧"长度对、CRC 错"的残帧，取决于丢了第几个字节 |
| 固件 pending 顶替（`s_drop`） | 恒 0（帧根本没成形，谈不上顶替） |
| 上位机 CRC 错 / 丢字节 | 恒 0（问题在 PC→MCU 方向） |
| 唯一稳定现象 | **这一条请求没有应答，下一条又好了** |

这也是为什么它拖了这么久没定位：除了"没应答"本身，没有任何计数器会动。

**A/B 实测**（同一份代码，只改 `CMD_Q_LEN`）：

| 队列 | 读块 128/256 次 | `q_ovf` | 固件 CRC 错 |
|---|---|---|---|
| 32 B | **3 / 128 失败** | **39** | 3 |
| 256 B | **0 / 256 失败** | 0 | 0 |

`q_ovf` 是本轮新加的计数（30082 只读槽 10）。32 B 时它长了 39，直接证明"字节被丢了"。

**修复**：`CMD_Q_LEN` 32 → 256（对应 2.8 ms 缓冲窗口，覆盖最长阻塞；RAM +224 B）。
同时补 `s_q_ovf` 计数 —— 以后再出现同类现象，先读这个数，不要再靠猜。

顺手修掉一个隐藏地雷：`ServoCmd_Init()` 的清零循环用 `uint8_t i` 配
`i < CMD_Q_LEN`，`CMD_Q_LEN=256` 时 `i < 256` 恒成立 → **死循环**。已改 `uint16_t`。

### 1.2 `build_x72.py -f` 只烧录、不编译（静默烧旧镜像）

**位置** `Agnet/build_x72.py`

UV4 的 `-f` 在这个工程里只做 Flash Download：日志里只有
`Load / Erase / Program / Verify OK`，**没有任何 compiling 行**，返回码仍然是 0。
脚本的 `must` 校验只在 `-r` 分支生效，所以 `-f` 一路绿灯。

**实测**：连续 4 次 `-f`（09:27、09:29、09:30…）之后
`X72_FOC.axf` 的时间戳还停在 **09:19**，而源码已是 09:30。
也就是说这 4 轮"烧录成功"跑的都是旧固件 —— 现象是"新加的诊断槽读不到、
`n_int` 还是旧值 9"。差一点把工具问题当成固件 bug 去查。

**修复**：`-f` 改为两步 —— 先 `-r` 全量编译（校验 `0 Error(s), 0 Warning(s)`、
校验关键文件确实被编译、校验 axf 时间戳在 10 分钟内），再 `-f` 烧录（校验 `Verify OK`）。
任一步失败即停。

### 1.3 上位机串口：没有 `write_timeout`、没有写锁、一次异常就断链

**位置** `host/mavlink_link.py`

三个问题叠在一起：

1. `serial.Serial(port, baud, timeout=0.2)` **没给 `write_timeout`**。默认 `None`
   时并发写会让 pyserial 内部状态卡死，抛 `SerialTimeoutException('Write timeout')`。
   （`thermal_soak.Rig` 在 2026-11-19 已经踩过同一个坑并写进注释，`SerialLink` 没跟上。）
2. `send()` **没有把 `s.write()` 串行化**。保活线程 5 Hz 与主线程命令必然撞车。
3. `_rx_loop` / `send()` 把**任何一次**串口异常当作致命错误 → `disconnect()`，
   `self.ser = None`，三个线程一起退出。现象是"读到第 21 块突然全部超时、
   所有线程消失、端口却还开着"，一次抖动废掉整场长测。

**实测**：修之前 64 块连读随机在 2/4/13/21 块处失败，`last_error` 为
`串口写入异常（第 2 次）：Write timeout`。

**修复**：
- `write_timeout=0.5`
- 新增独立的 `wlock`（不复用状态锁 `self.lock`，那是接收线程解析每帧都要拿的）
- 读异常改为连续计数重试（连续 400 次 ≈10 s 才断链），与 `thermal_soak.Rx` 同一策略
- 写异常**不自动重发**（30069 这类动作帧重发会多执行一次辨识），只报错；连续 8 次才断链
- 新增 `serial_err / serial_err_total` 计数，并入 `_parser_stats()`

## 二、功能补齐

### 2.1 30094 `op=2` 停止录波

`Servo_StopRecord()` 只清使能、**不清 `s_rec_n`** —— 半截波形仍然可读，这正是
"看着不对想立刻停下看"的用法。语义：

- `op=2` 且正在录 → 停止，回 `n_pts`（已采点数）
- `op=2` 且已停 → 幂等成功；若从没采过（n=0）回 `status=1`
- 停止后 `op=3` 可直接取已采的部分（`n_blk` 按实际点数重算）

**实测**（`verify_record.py` [5]）：

```
START(div=100) → 0.6 s 后 state=1 n=124
再 START      → "正在录波"（忙互斥）
op=2 STOP     → n=141，0.6 s 后仍 141（确实停了，不是只置标志）
重复 op=2     → ok（幂等）
```

### 2.2 位置补偿三参数迁到 30082（替掉 0x04 帧）

float 通道 16 槽已满，而 30082 的载荷是硬布局（16f+16u32+16i32=192 B），
加 float 槽要改两边协议。改用**整数通道的空槽**，单位 mrad：

| 槽 | 名字 | 含义 | 上限 |
|---|---|---|---|
| 6 | `comp_mrad` | 补偿量 | 100 mrad |
| 7 | `comp_min_mrad` | 行程阈值 | 100 rad |
| 8 | `comp_en` | 补偿使能 | 0/1 |

选 mrad 的理由：补偿量本身是 0~50 mrad 量级，1 mrad 分辨率对定位足够，
且原 0x04 帧的回显本来就是 mrad，换算不改变精度观感。

### 2.3 0x04 / 0x02 两个私有小帧入口关闭

一条 `#if X72_ASCII_DEBUG` 同时关掉（两个 `if` 在同一个开关里，同生共死）。
关的理由不是洁癖：

1. 它们是**绕过飞控协议的第二入口**。0x02 MIT 帧虽然也走 `mit_engage()`，
   但写完没有任何应答 —— 上位机无法确认到底进没进环。
2. 能力没丢：PCMP 三参数已迁到 30082 且能读回（原来写完只能看一行 ASCII 回显）。

**实测**（`verify_legacy_frames.py`，7/7）：
用 30082 把 `comp_mrad` 设成 20 → 发 0x04 帧要求 50 mrad → 读回**仍是 20**。
（ASCII 打开时这一帧会把补偿量改成 50 并回 `[CMD] PCMP comp -> 50.00mrad`。）

### 2.4 `ExecAction` 返回码细分

原来只有 1/0 两种，于是"还在闭环里、请先封锁"和"没有这个动作号"都回
`OUT_OF_RANGE`。现场看到 `OUT_OF_RANGE` 只会怀疑动作号写错，不会想到是联锁拒绝。

| 返回码 | 含义 | 30069 应答 |
|---|---|---|
| `SC_EXEC_ACCEPT` (1) | 已入队 | `SUCCESS` |
| `SC_EXEC_REJECT` (0) | 动作非法/子模块拒绝 | `OUT_OF_RANGE` |
| `SC_EXEC_NEED_DISARM` (2) | 仍在闭环 | `WRITE_STATE_ERROR` |

联锁本身**没有放宽**（比 ASCII 更严是故意的：`armed=1` 表示上位机打算闭环，
此时插一次标定等于在环里改零点）。上位机 `action()` 对 status=3 直接给出
"先 `set_controlword(0, halt=1)` 再发动作 N"。

**实测**：

```
en=1 时发 CAL(4)   → status=3 WRITE_STATE_ERROR（中文提示已带出）
封锁后发 ABORT(14) → status=0 SUCCESS
非法动作 99        → 上位机层就拒（不在 0..14）
```

## 三、新增的 4 个只读诊断槽（30082 整数通道 9~12）

这次排查最大的教训不是那个缓冲，而是**"丢了却没有任何计数"**。补上：

| 槽 | 名字 | 含义 | 正常值 |
|---|---|---|---|
| 9 | `link_diag` | 高 16 位 = `s_drop`（pending 被顶掉）；低 16 位 = 长度/CRC 错 | 0 |
| 10 | `q_ovf` | 命令环形缓冲溢出丢的字节数 | 0 |
| 11 | `uart_err` | USART 错误标志累计（ORE/FE/NE/PE） | 0 |
| 12 | `rx_ok` | 已成功分发的帧数（单调增） | 递增 |

分工是刻意的，四条各自指向不同的排查方向：

- `q_ovf` 涨 → 主循环有超过缓冲窗口的阻塞（查阻塞源，**不是**加大缓冲了事）
- `uart_err` 涨 → 硬件 RDR 没被及时取走（查关中断临界区/中断优先级）
- `link_diag` 低半字涨 → 字节在链路上丢了，或长度与 `s_meta` 不一致
- `link_diag` 高半字涨 → 主循环来不及取，帧被下一帧顶掉
- `rx_ok` 不涨而请求照发 → 请求根本没到（先怀疑发送侧/端口）

只读是故意的：`set = NULL`，30082 写它会拒并计入 `s_locked`。

- **结构层**：op 语义、忙互斥、块边界（末块 16 点、越界块 `n_this=0`）

  实测 **37.49 rad，误差 0.1%** —— 一条判据同时校验了 div 时基、通道选择、
  角度编码三件事。任何一项错都会差 5 倍以上（div 错 5 倍；通道错拿到的是电流；
  角度按 int16 而非 uint16 解会得到完全不同的斜率）。

## 六、待跟进 #5 判断为"不改"（原判断有误）

原文写"`rec_pump`/`mech_task1ms` 仍做字符串格式化，辨识结束后 30~43 ms 空转"。
逐条查完，结论是**这条不该改**：

- **`rec_pump` 根本进不去**：`s_rec_phase` 只在 ASCII 的 `&` 分支里被置 1，
  ASCII 关闭后永远是 0，函数第一句就 `return`。30094 的 `op=1` 走的是
  `Servo_StartRecord()`，不碰 `s_rec_phase`。所以"空转"不存在。
- **`mech_task1ms` 不能拆**：它的文本格式化与 `Telemetry_PushIdentResult()`
  **在同一段代码里**（"全部发完"那一支），而且齿槽那一行里还夹着
  `CogFf_LoadFromIdent()` —— 关掉文本就等于关掉装表。收益（失能态下几十毫秒
  的格式化）远小于风险。保留，并在代码里注明原因。

## 七、待跟进 #4：49 个 `Rig` 脚本（未做）

先纠正一个事实：`thermal_soak.Rig` 本身**已经是 MAVLink 的**（`send()` 组 MAVLink 帧、
`Rx` 线程解析 30025/30027/30040/30054/30069），只有 `rl_ident()` 还在发 ASCII `@`。
脚本失效是因为它们**直接往 `rig.s` 写 ASCII**，统计到的命令词汇是：

```
= <rpm>   27 处      D        25 处      S   21 处      Z  12 处
& 8 处     P 5 处     ! 3 处     X/W/U/C/@/+ 各 1~2 处     } ` N M F E > : 各 1 处
```

两条路线，我的判断：

| 路线 | 做法 | 问题 |
|---|---|---|
| A | 给 `rig.s` 套一层"ASCII → MAVLink"代理，并按 100 Hz 合成 `[CMD] st/spd` 文本 | 脚本零改动，但要**伪造** S/K/`[REC]` 行的格式与取值口径。19 个字符里任何一个合成错，脚本会拿着错数继续跑 —— 这类"看起来跑通了但值不对"正是这轮审查反复在抓的东西 |
| B | 只把长期要用的 ~8 个改成高阶 API（`status()`/`run()`/`rec_read()`） | 干净，逐个改；改完能顺带把判据也升级 |

**建议走 B**，并先把 4 个最常用的（`bringup_1000`、`thermal_step`、`combo_sweep`、
`deadband_matrix`）改成模板，其余按需。理由：这批脚本都是诊断脚本，重跑一次的代价
远小于"合成文本口径漂移"的代价。这一条留到你确认后再动。
