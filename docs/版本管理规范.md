# 版本管理规范

适用于 `X72` 仓库内的固件、上位机脚本与硬件资料。目标是让"现在跑的是哪个版本、
它验证过什么、能不能安全升级"这三个问题在任何时候都能回答。

---

## 1. 版本号规则

采用 `MAJOR.MINOR.PATCH`，但**判定标准按嵌入式固件的实际破坏面来定**，不按代码量：

| 位 | 触发条件 | 现场后果 |
|---|---|---|
| **MAJOR** | ① `PS_VERSION` 升级（`ParamBlob` 结构变）<br>② MAVLink 消息的**长度或 `crc_extra`** 变更<br>③ CAN FD 的 ID 布局 / 帧布局变更<br>④ 控制字、状态字、模式号的语义变更 | 上位机解析崩 / 现场标定（cal、z、ψ、齿槽表）全部作废 / 主站不兼容 |
| **MINOR** | 新增控制模式、新增消息、新增辨识项、新增保护项、新增可调参数槽位 | 向后兼容，旧上位机可继续用 |
| **PATCH** | 修 bug、调整默认参数、改文档、加诊断、性能优化 | 无接口变化 |

**灰色地带的裁定**：

- 改默认参数值（如 `POS_AMAX` 200→30）→ **PATCH**。它改变了行为但没改接口。
- 新增 `s_meta[]` 条目（新消息号）→ **MINOR**。老上位机不认这条消息不会崩。
- 给已有消息**追加**载荷字段但总长不变 → **MAJOR**。上位机按固定偏移解析，会读到脏数据。
- 只改注释、只改文档 → **PATCH**，也可以攒着等下次一起发。

## 2. 版本号的单一真源

> ⚠ **当前缺口**：固件里没有任何版本号常量，只能靠 Code size 和 git 提交反查。
> 这是版本管理落地前必须先补的一项。

### 目标做法

在 `Board/app_param.h` 定义唯一真源：

```c
#define FW_VERSION_MAJOR   (1)
#define FW_VERSION_MINOR   (0)
#define FW_VERSION_PATCH   (0)
#define FW_VERSION_STR     "1.0.0"
```

并让它**能从总线读到**，否则现场无法确认板子里烧的是哪一版：

- 首选：`30055 AppStatusInfo` 的空闲字节（现在 46 B 里 `p[44]` 已放 `active_mode`、
  `p[45]` 放链路自愈计数，需另找位置或扩长）
- 备选：`30090` 的 `drop` 字段之后追加，或新开一条 `30099` 版本信息（≤16 B）

### 版本号变更的配套动作

1. 改 `app_param.h` 的三个宏
2. 改本文件与 `README.md` 的"当前版本"
3. 在 `CHANGELOG.md` 顶部加新条目
4. 打 tag（见 §6）

**只改一处等于没改** —— 这四条必须同一次提交内完成。

## 3. 提交信息规范

`<type>(<scope>): <subject>`

| type | 用于 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `perf` | 性能/纹波/精度优化，不改接口 |
| `refactor` | 重构，不改行为 |
| `docs` | 文档 |
| `test` | 测试脚本、诊断工具 |
| `chore` | 构建、目录、依赖、`.gitignore` |

`scope` 用模块名：`servo_isr` / `pos_loop` / `can_proto` / `mavlink` / `ident` / `docs` / `build`。

**subject 要写"改了什么导致什么"**，不要写"修改代码"：

```
✅ fix(servo_isr): MIT 30066 用缓存 p=0 重发给定，上刚度瞬间撞 0x0020
✅ fix(can_proto): TestStop 停在 INIT 导致节点永久退出总线
❌ fix: 修了一些问题
```

修 bug 的提交，**优先把根因写进 subject，把实测数据写进 body**。
本工程的判据通常是数字（`TEC=0`、`iq 峰 4.47→1.18 A`），这类信息比"已修复"有用得多。

## 4. 分支策略

单人为主的项目，不搞复杂流程：

| 分支 | 用途 |
|---|---|
| `main` | 可发布状态。每次推上去都应是"能烧、能跑、标定齐全" |
| `feat/<简短名>` | 跨多次提交的功能开发，完成后合回 `main` |
| `fix/<简短名>` | 需要多轮验证的 bug（例如 CAN 双节点问题） |

直接在 `main` 上改小 bug 是允许的；**但只要这次改动需要烧录验证超过两轮，就开分支**，
避免 `main` 长时间处于不可用状态。

合并用 `--no-ff` 保留分支轨迹，方便回溯"这个功能是哪一批提交做的"。

## 5. 固件发布的必查项

每次发版本（打 tag 前）逐条确认，**任何一条不满足就不发**：

### 5.1 构建

- [ ] `PROD_BUILD=1` 编译通过，记录 `Code` / `RO` / `RW` / `ZI`
- [ ] 开发构建（`PROD_BUILD=0`）也编译通过（否则以后没法调试）
- [ ] 判成败用 `grep "0 Error(s)"`，**不要看退出码** —— 生产构建的 `#warning` 会让 UV4 返回 1

### 5.2 烧录后（每次都做）

- [ ] `30090` 的 `fault = 0`
- [ ] `30090` 的 `flags` 含 **bit0(CAL) + bit1(ZERO) + bit7(COG)** 三位
- [ ] 若烧录后 COG 位消失 → 齿槽表被擦，需重做 `action=13`；CAL/ZERO 丢失需重做 `4` / `5`

> `UV4 -f` 有概率擦参数页，这不是偶发传言，2026-11-22 实测遇到过。

### 5.3 功能回归（最小集）

- [ ] 四个模式各起环 5 s，无故障（POS / VEL / TORQUE / MIT）
- [ ] MIT 按"零刚度起环 → 贴当前位置 → 上刚度"顺序，`fault` 保持 0
- [ ] 位置模式从 3.0 rad 走到 0，无 0x0100
- [ ] 速度模式 100 rpm / 1000 rpm 各 10 s，`wmeas` 跟随
- [ ] 若本次改了辨识相关代码：`Z` 跑一次，极对数为整数、`resid < 0.1`

### 5.4 记录

- [ ] `CHANGELOG.md` 新条目（含实测数据）
- [ ] `README.md` 的"已知限制"是否需要更新
- [ ] 版本号三处同步（`app_param.h` / 本文件 / `README.md`）

## 6. Tag 与发布

```bash
# 1. 确认工作区干净
git status

# 2. 打附注 tag（不要用轻量 tag，附注能记录发布说明）
git tag -a v1.0.0 -m "v1.0.0: 四模式 + MAVLink + CAN FD L1

构建: PROD_BUILD=1, Code=111124
实测: 四模式起环通过, Z pp=14/resid=0.023, 齿槽 512 箱 valid=1
已知: CAN FD 双节点不通, 5/7 次谐波自激"

# 3. 推送提交与 tag
git push origin main --follow-tags
```

tag 名与 `FW_VERSION_STR` **必须完全一致**（含 `v` 前缀仅在 tag 上，宏里不带 `v`）。

GitHub Release 的说明直接摘 `CHANGELOG.md` 对应段落，不要另写一份。

## 7. 固件状态标识：Code size 与参数页

除了版本号，本工程还有两个**只有它能说明问题**的标识，每次发布必须记录：

| 标识 | 怎么取 | 为什么重要 |
|---|---|---|
| **Code size** | 编译日志的 `Program Size` | 定位"板子里到底是哪一版"。改了代码但 Code 没变，通常意味着分支没编译进去（`#if` 宏顺序踩过这个坑） |
| **参数页状态** | `30090.flags` 的 bit0/1/7 | 标定是否齐全。丢了 COG 不会报错，只会让低速纹波变大 —— 容易被忽略 |

建议在 `CHANGELOG` 每个版本末尾固定写：

```
构建：PROD_BUILD=1，Code=111124 RO=3350 RW=2240 ZI=27564
烧录后：flags=0xDB（CAL/ZERO/COG 齐全），fault=0
```

## 8. 回滚

| 场景 | 做法 |
|---|---|
| 只想退回上一版固件 | `git checkout v1.0.0 -- Firmware/` 后重新编译烧录 |
| 参数页已被新版本升级（`PS_VERSION` 变了） | **不能直接回滚**，旧固件读不懂新 blob，会被判无效并回默认值 → 必须重做全部标定 |
| CAN / MAVLink 协议改动后发现主站不兼容 | 回滚固件 + 同步回滚上位机，两者必须同版本 |
| 只是某个功能有问题 | 优先用 `PROD_BUILD` 或运行时开关（`cog_en` / `harm_en` / `deadband_en`）关掉，而不是整体回滚 |

**任何时候不要对已推送的 `main` 做 `force push` 或 `amend`**。回滚用 `git revert` 生成反向提交，
保留"曾经发布过什么"的完整痕迹 —— 现场排查依赖这个。
